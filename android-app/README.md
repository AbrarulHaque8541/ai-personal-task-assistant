# Daymark Android V1

A native, single-user Android app with local-first task management and an HTTPS-only embedded browser that connects only after a user action. This is a separate Android project under `android-app`; the existing web prototype in the parent directory remains intact.

## Standalone GitHub APK updater (release-gated)

The updater code is separate from task storage. It checks only the fixed public [GitHub latest-release endpoint](https://api.github.com/repos/AbrarulHaque8541/ai-personal-task-assistant/releases/latest), at most once per 24 hours from `MainActivity.onResume`, or when the user taps **More → Check now** (which bypasses the interval). It never polls in the background and never includes task contents or history in a request; no app telemetry is implemented. This is not a zero-egress claim: when enabled, the app contacts GitHub for release metadata and, only after download consent, obtains the APK from the GitHub release asset through a bounded allowlist of HTTPS GitHub asset hosts. Metadata checks stay disabled in debug builds and unless the trusted publisher signer is pinned and the updater gate is explicitly enabled. The common manifest declares `INTERNET`; `githubSideload` additionally declares `ACCESS_NETWORK_STATE`, which the Play flavor does not inherit. Neither `REQUEST_INSTALL_PACKAGES` nor a `PackageInstaller` handoff is present.

Before any APK download, the app shows the release name/version/notes and exact declared byte count, then asks for a per-download network choice: **Wi-Fi only (recommended)** is selected by default, or the user may explicitly **Allow mobile data**. The Wi-Fi-only choice is checked before opening each HTTP request and while copying the response; a change away from Wi-Fi stops the download. The user must separately choose **Download and verify**; Cancel starts no APK transfer, and retries are never automatic. After size, hash, package, version, min-SDK, and exact signer checks pass, Daymark offers Android's document picker to save the verified APK to a user-chosen location. The picker suggests a unique `Daymark-v<version>.apk.daymark-pending-<token>.tmp` title, so an empty picker-created document is not a final-looking APK. A compact digest/version/token/name transaction reference is saved in Activity instance state; release metadata and the verified APK stay in the existing app-private recovery record, and no SAF URI or credential is saved. On result, Daymark revalidates the retained artifact, operates only on the returned URI, stages it under `.daymark-incomplete-<token>` before writing, checks size/digest during copy, independently reopens and verifies the destination bytes, and only then requests finalization. If the provider returns the suggested title unchanged, the default name becomes `Daymark-v<version>.apk`; a user-renamed title is preserved. Daymark never resolves or opens an existing document by a guessed name; final-name collision handling is delegated to the provider rename result, and real-provider collision behavior remains unverified (the host fake refuses a collision without changing the existing item). If callback state is missing, Daymark operates only on the exact new URI returned by this `ACTION_CREATE_DOCUMENT` request: it best-effort renames that document to a unique orphan `.tmp` marker and then deletes that exact URI; it never searches for or deletes by display name. If the provider rejects both rename and deletion, cleanup cannot be guaranteed and provider-dependent residue may remain. **Process-death limitation:** If the process dies after the `ACTION_CREATE_DOCUMENT` result but before SAF saving finishes, an incomplete document may remain—under the picker-selected name (normally the suggested `.tmp` title, unless renamed by the user) before staging or the `.daymark-incomplete-<token>` marker once copying starts. The result URI/access grant is not persisted, so automatic resume or guaranteed cleanup is unavailable; residue and cleanup depend on the provider and are unverified on real Android. The verified app-private source remains available for retry or explicit discard. SAF finalization is not guaranteed atomic. Daymark does not open an installer, request install-source access, or install the APK. The user must open a successfully saved file themselves; Android controls any source approval and final confirmation. The current `UpdaterPublisherConfig` gate is enabled for the signed sideload flavor and pins the expected production certificate SHA-256. The updater remains release-only and signer-gated; the exact-tag production workflow and on-device behavior must still be verified before claiming operational update behavior. Host fake-provider fixtures cover transaction serialization, interruption, finalization, destination read-back, and collision handling; they cannot replace real APK signer parsing or device/provider testing.

### Stable-release publishing prerequisites

1. Publish a non-draft, non-prerelease GitHub Release with one `.apk` asset whose GitHub API `digest` is `sha256:<64 hex characters>`. The version tag must be `vMAJOR.MINOR.PATCH`; the APK `versionName` must match the tag, `versionCode` must exceed the installed app, and the APK application ID must be `com.cue.daymark`.
2. Include this machine-readable block in the release body, followed by human-readable notes. `minSdkVersion` must match the APK manifest and be supported by the device; `signerCertificateSha256` is the APK signing certificate SHA-256 fingerprint.

   ```html
   <!-- daymark-updater-v1
   {"applicationId":"com.cue.daymark","versionCode":2,"minSdkVersion":26,"signerCertificateSha256":"<64 lowercase hex characters>"}
   -->
   ```

3. Keep the production signing key in protected GitHub Actions secrets only. Main CI run #314 validated the configured secrets and confirmed that the signed candidate APK matched the pinned publisher certificate. Never expose or commit key material. Debug APKs are signed with a different key and **must never be used as the update target**. Keep the exact same production signer across releases: this updater requires exact certificate continuity and does not implement or verify signing-key rotation lineage. Any rotation must remain fail-closed until separately designed, reviewed, and tested.
4. The owner-selected path is verify/download plus a user-selected save and manual opening. `REQUEST_INSTALL_PACKAGES`, the Android `PackageInstaller` API, and app-launched install-source Settings are not part of this PR. The user—not Daymark—opens the saved APK from Files; Android may require the user to approve the source and confirm installation. Device behavior for that manual route is still unverified.
5. Before offering a saved APK, require the downloaded length and SHA-256 to match GitHub release metadata, and verify package ID, version name/code, min SDK, and signer SHA-256 against both release metadata and the running app. Recheck size and digest while copying to the user-selected document; any mismatch fails closed. Never ask the user to uninstall to force an update.

Daymark stores tasks encrypted with an Android Keystore key. Uninstalling clears that file/key, and changing the app's signing identity can make an update impossible or risk loss of access to encrypted local tasks. Preserve the same production signing identity across releases, and **do not uninstall Daymark as a workaround**. The historical `v1.0.0` GitHub Release has no attached binary asset. The latest published release is v1.0.4 with APK/AAB assets. v1.0.5 is a source candidate only until its exact tag workflow publishes it.

## V1 experience

- **Simple path (default):** the first screen asks “What do you want to get done?”, gives an everyday example, and offers an editable text field with a one-tap Add action. A new quick-added task starts with no due date and medium priority; that default is stated on screen. **Add with a date or priority** opens the same editable task form with the draft filled in.
- **Power path:** an explicit top-bar switch reveals title search, All / Today / Upcoming / Completed filters, and deterministic Demo suggestions. It uses the **same task records** as Simple; changing paths does not copy, transform, or hide stored data.
- Both paths support task edit, completion, and deletion. Deletion asks first and can be undone for seven seconds. The task editor has Cancel and system Back behavior.
- Attachments support user-selected photos, audio, video, PDFs and other provider-openable documents. They are copied into the app and encrypted at rest. Daymark has no in-app preview and never executes a file. Only files matching a limited MIME/extension allowlist are offered through a **user-confirmed** “Open with another app” chooser; all files remain untrusted, and active, executable, installer and unknown types are not handed to another app.
- Local status is visible. Text entry and date/priority remain editable before saving; a visible message explains the next step after a quick add.
- **Web mode:** the shared composer switches explicitly between Task and Web. DuckDuckGo is the default search engine, with Google, Bing, and Brave Search available; ChatGPT, Claude, Gemini, and Perplexity are plain website shortcuts. Search terms or destinations load only after Go/a site tap. Entering Web mode clears the visible task draft; Daymark retains it locally and restores it only when returning to Task. Website sign-in and compatibility depend on each provider.\n- **Extensions:** compatible Daymark packs and userscripts can inject page-local CSS/JavaScript on matching HTTPS sites. Before an imported pack is stored, Daymark now shows a review with match scope, CSS/JS size, run timing, parser warnings, and a **Trust & add** confirmation. Imported scripts can read/change matching page content and may send page-visible data externally; import only code you trust. This is not a full Chrome/Firefox extension engine.

## Accessibility and settings

The app uses native Android controls, descriptive TalkBack labels, scrollable content, keyboard/IME submission, and touch targets of at least 48 dp for primary actions, filters, task controls, and search clearing. **More** uses grouped, descriptive settings rows for appearance, text size, high contrast, accessibility, permission status, encrypted backup/restore, browser/extensions, and update checks, with a restrained entrance transition. Browser Settings includes Safe Browsing and an opt-in **Block network images (save data)** switch; toggling it applies to current and new WebViews. Turning it on does not hide images already rendered until the page is reloaded; turning it off can allow previously blocked images to load automatically. This does not block every ad or tracker. When a page is loaded, **Reader mode** uses a bounded DOM tree walk to extract up to 60,000 characters from an article/main/body heuristic into a native selectable-text dialog; it does not clone or mutate the page DOM, render site HTML, run extracted text as code, or make another network request. The separate **Expand** action opens the live page full-screen. Dynamic pages and non-article pages may extract imperfectly. Browser controls are labeled; device-level TalkBack traversal and visual rendering remain untested.

Language is **English-only UI** in this prototype; dates use the device locale. Other translations and right-to-left review are not complete. The screen-reader item points to native Android/TalkBack support; it does not replace Android's accessibility settings. V1 has no custom looping/auto-playing motion, so Android system reduced-motion behavior applies to platform UI; there is no separate in-app reduced-motion switch.

## Local-only operation and content policy

The shared manifest declares normal `INTERNET`; the Play flavor inherits it, and `githubSideload` additionally declares `ACCESS_NETWORK_STATE` for its foreground updater. Core task flows need no permission and task data stays local. The updater does not upload task data/history and has no background poller. Its source gate is enabled for the signed sideload flavor, with the production certificate pinned; the exact-tag production workflow must verify the signer before release. There is no provider account, sync service, background inference, or model/locale/plugin downloader. Core task flows are designed for offline use, but airplane-mode behavior still requires on-device runtime testing before being called verified.

**More → Permission status** reads the installed app's declared permission list; task capture, edits, completion, deletion, and encrypted storage need no permission. Both the shared and Play merged manifests include `INTERNET`; the `githubSideload` variant also includes `ACCESS_NETWORK_STATE`. This screen is read-only: it does not request, grant, manage, revoke, or automatically enable access. A full permission center is proposed/deferred, not present in the current source. The updater never requests `REQUEST_INSTALL_PACKAGES`; Android—not Daymark—controls any approval when a user manually opens a saved APK. If a future feature needs protected access, explain why and request only the minimum when the user chooses that feature; runtime permissions require the Android system prompt and the user's decision, while special app access must be granted by the user in Android Settings. If access is denied, keep the rest of the app usable, explain the affected feature without repeated pressure, and offer the applicable Settings route for revocation or reconsideration. An ordinary app cannot silently grant itself arbitrary system-level access or bypass the platform's privileged/signature-only grant rules. Do not describe an “autopilot” that requests or accepts everything ([Android permissions overview](https://developer.android.com/guide/topics/permissions/overview), [runtime requests](https://developer.android.com/training/permissions/requesting), [special access](https://developer.android.com/training/permissions/requesting-special), [manifest protection levels](https://developer.android.com/guide/topics/manifest/permission-element)).

Task capture, editing, filters, completion, deletion, undo, and encrypted task storage remain on-device and need no Android permission. The shared manifest declares normal `INTERNET` for Android System WebView; the `githubSideload` flavor also contains the separately gated updater client. Browser access is ready by default, but no page request occurs until a separate **Go** or site-shortcut tap. The removed Online/Offline control is not shown; legacy saved Offline preferences are migrated so users are not silently blocked. HTTPS-only navigation and the internal page/resource-load gate remain enforced. Backgrounding Daymark stops and closes the current page. The Safe Browsing setting does not control the platform-managed Android System WebView Safe Browsing service, which may contact Google/Play Services for version/device-dependent hash or update checks. The provider itself is not selectable in Daymark; users can separately turn the Safe Browsing feature on/off in Browser Settings. Search/page requests and normal connection data such as IP address and browser identification go to their selected destinations; loaded pages may request content from their own or third-party endpoints. Those providers and sites may log requests. Daymark adds no app analytics, task sync, automatic task transfer, background search, or browser prefetch. Task-mode text is cleared from the shared composer on entry to Web and restored only inside Task mode.

The default search engine is DuckDuckGo; Google, Bing, and Brave Search are optional choices. Bare domains are promoted to HTTPS. Explicit `http://` inputs, non-HTTPS top-level links, and HTTP redirect/downgrade navigations are rejected with an unsupported/insecure message; the manifest keeps `usesCleartextTraffic="false"`. Per-site HTTP exceptions would need a separate explicit request. Safe Browsing is enabled by default and can be disabled from **Browser Settings** only after a warning; the preference is saved locally and applied to current and future Daymark WebViews. The setting changes browser protection and does not change Daymark's page/resource-load policy; the platform-managed Safe Browsing provider is not selectable in Daymark. The WebView also blocks mixed content and file/content access, cancels certificate errors, denies camera/microphone/location requests, and disables pop-ups and downloads. Google Safe Browsing may use version-dependent URL-hash-based checks: WebView M126+ may send a partial URL hash through a proxy for real-time checks; earlier versions use a local partial-hash database and may query a server on prefix match. This is not a claim that every full URL is sent; the method depends on WebView version and device settings. The manifest opts out of WebView diagnostic metrics. See Android's [WebView guide](https://developer.android.com/develop/ui/views/layout/webapps/webview), [Safe Browsing guidance](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview), [WebViewClient navigation behavior](https://developer.android.com/reference/android/webkit/WebViewClient), and [network security configuration](https://developer.android.com/privacy-and-security/security-config).

Site history keeps at most 50 validated HTTPS origins (scheme, lowercase host, and non-default port) in app-private preferences; it is local but not encrypted. Paths (including reset/OAuth routes), query values, fragments, URL userinfo, and page titles are never stored. Legacy entries are reduced to origins on launch, and repeat visits to one origin collapse into one entry. Selecting a saved site opens its origin, not the prior route; recording history does not alter the full validated URL used by the active WebView. **Site history** clears these entries, the current WebView back/forward list, its resource cache and SSL exception preferences, plus cookies and Web SQL/HTML5 Web Storage across all websites used in Daymark. Cookie deletion is asynchronous. `WebView.clearFormData()` only dismisses a currently open autocomplete popup; saved Android Autofill or password-manager data is not cleared. Other apps' browser data and records retained by remote sites/search providers are outside the action ([WebStorage.deleteAllData](https://developer.android.com/reference/android/webkit/WebStorage), [CookieManager.removeAllCookies](https://developer.android.com/reference/android/webkit/CookieManager)).

**More → Permission status** reads installed-app declarations and is read-only; it does not request, grant, manage, revoke, or automatically enable access. The shared manifest's `INTERNET` permission is used by WebView; the gated updater code also uses the network in the sideload flavor. Task operations do not depend on Internet access, and the app does not request camera, microphone, location, storage, or other runtime permissions. Offline task behavior and browser compatibility still require on-device testing. An ordinary app cannot silently grant itself arbitrary system-level access or bypass Android's privileged/signature-only grant rules ([Android permissions overview](https://developer.android.com/guide/topics/permissions/overview), [manifest protection levels](https://developer.android.com/guide/topics/manifest/permission-element)).

Make the app UI itself usable with TalkBack and other accessibility tools; do not request `AccessibilityService` as a generic permission or plugin workaround. Android positions that service for assistive technology, and broad event monitoring can be resource-intensive. Keep it deferred unless a concrete assistive use case is approved, then require separate user opt-in, security review, and device testing ([AccessibilityService guidance](https://developer.android.com/guide/topics/ui/accessibility/service)).

**No optional content ships in V1:** no GGUF weights, voice/language packs, compiled inference runtime, plugin packs, bundled demo content, or other model artifacts. The app's small vector launcher icon is UI chrome, not an optional pack. Optional pack sizes are **N/A (none exist)**. A base release APK target of **<15 MB** remains unmeasured until a genuine release build is measured. No APK/AAB is tracked in the repository. The published v1.0.4 release has signed APK/AAB assets; v1.0.5 remains an unpublished source candidate until its exact-tag workflow succeeds.

The app performs ordinary foreground UI, file, Keystore, and—only after an explicit Web action—WebView/network work, so literal zero device load is impossible. There is no app-owned background task, polling, inference, telemetry, or download path. Near-zero idle/background work is a design target, not a measured battery claim.

## Task storage and demo suggestions

Task records use schema-versioned JSON encrypted in `files/tasks.enc` with AES-GCM and an AES key kept by Android Keystore. The reader accepts existing schema v1 task data; current writes use schema v2 to include attachment references. Keys are non-exportable; secure-hardware backing depends on the device. Disk and cryptographic operations run on one background executor. A truly absent store is a valid empty list; malformed data, an unavailable key, or authentication/read failure is a distinct fail-closed state. The app does not replace a missing key for existing ciphertext. Writes use Android `AtomicFile` and its commit/failure path, not a non-atomic replacement fallback. If a save fails, the attempted change remains visible and is explicitly labeled unsaved while edits are paused; leaving the app may discard that visible change. The last committed encrypted snapshot remains the store's committed version, but durability across sudden power loss or every Android implementation is not established.

## Task attachments

Choose **Files · N** on a task to attach one photo, audio clip, video, PDF, or other openable document at a time through Android's `ACTION_OPEN_DOCUMENT` system picker. Daymark reads the selected provider stream once and copies it into `noBackupFilesDir/attachments` as a streaming AES-GCM encrypted payload. The v2 payload format's length-delimited AES-GCM associated data binds the canonical app-owned blob ID and owning task ID, so copying ciphertext under another attachment ID or associating it with another task fails authentication. It does not retain the provider URI, provider path, or persistable permission grant; the separately authenticated task snapshot stores only an app-owned ID and sanitized display name, MIME type and measured byte size. A separate Android Keystore key protects payloads, and the attachment folder is outside Android backup even if backup configuration changes later. The unshipped development-only v1 payloads created before this binding are not migrated and fail closed; no release compatibility is claimed.

The manager shows limits before the picker: **20 MiB per file, 100 MiB total, 100 files overall and five files per task**. Both provider size hints and actual streamed bytes are checked; the total limit uses the snapshot's remaining quota and does not trust provider metadata. Import can be cancelled while copying; once the atomic task-reference save starts, cancellation is disabled. Low free space, revoked/missing providers, stream errors and oversize files abort without committing the task reference. Plaintext is never staged: the temporary file is encrypted while streaming, removed on failure, and orphaned encrypted payloads are swept after a successful task load. Removing an attachment saves its task metadata before deleting the local encrypted file. Deleting a task waits until the deletion is saved and its seven-second Undo window expires before cleanup. Missing payloads are identified as unavailable and can be removed without clearing other task data.

To open a supported attachment, the user must tap **Open with another app**, accept a warning and choose a handler. Daymark shares a read-only, temporary content-URI grant backed by an authenticated decrypted pipe; it creates no plaintext temp copy. External applications may retain shared data, and streaming/seek support varies by handler. SVG/HTML/script, installer/executable, macro-enabled and unknown MIME/file types are blocked from this route. Formats outside the allowlist remain safely stored and removable, but cannot be opened from Daymark. These 20 MiB/100 MiB limits are prototype guardrails; larger media and broader format support need a separately tested policy.

Attachments remain local unless the user explicitly exports them in a portable backup. A missing or invalidated device Keystore key still has no recovery path for the app's existing local task snapshot; a portable archive is independent of that key only when a backup was previously created and its separate recovery key is available. Selecting an item from a provider for attachment is not Daymark export, cloud sync, or app-data backup.

## Portable encrypted backups (present in `main`; device/release qualification pending)

Use **More → Encrypted backup / restore**. Export and import happen only after explicit taps through Android's `ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT` pickers. While an import is waiting for its recovery key or running, the app temporarily keeps that document's URI and persistable read grant; it saves only the URI in activity state so the prompt can return after recreation, never the recovery key, and releases the grant when the import is canceled or finishes. It does not retain the archive, run a vendor login/network client, upload data, or sync. The document provider the user chooses may be remote and use its own network or sign-in. The `.dmbackup` archive is a bounded, pathless binary format (not ZIP), with a fixed magic, version/suite, and random backup ID. Its complete streamed input/output is capped at 110 MiB; attachment payloads are capped at 20 MiB each and 100 MiB total, with at most 100 attachments overall and five per task. Import enforces actual streamed bytes rather than trusting provider size hints. Each record uses AES-256-GCM with a full 128-bit tag, a fresh unique 12-byte nonce, and an HKDF-SHA-256-derived per-record key bound to the backup/header/record context. The manifest and complete record set are authenticated; import rejects unsupported versions/suites, oversize data, duplicates, malformed references, truncation and trailing bytes.

Task text, attachment names, MIME types and contents are encrypted. The outer format/version, backup ID, record-type flags, record count, exact attachment byte sizes and opaque task-association tokens remain visible. The export dialog explicitly discloses this metadata. Attachments are locally decrypted and encrypted into the archive; import fully authenticates and privately stages the entire archive before re-encrypting each attachment under the destination app's non-exportable Keystore key. Imported task and attachment IDs are newly generated; restore is add-only and never replaces existing tasks. A non-backed-up local journal records the pending transaction and imported backup IDs: encrypted blobs are committed first and the task snapshot via `AtomicFile` last. Startup reconciliation either removes unreferenced imported blobs or recognizes a committed snapshot before normal orphan cleanup. Reimporting an already imported backup on this device is blocked.

Each export creates a fresh, exactly 32-byte CSPRNG recovery key and displays a checked, grouped `DMK1-…` code once before writing the archive. The user must acknowledge saving it separately from the archive; Daymark does not verify or store that copy. The key is not placed in preferences, saved activity state, task data, archive headers, logs or clipboard, and in-memory byte buffers are cleared on completion/cancel. Anyone with both archive and key can read its contents; losing the key makes that archive unrecoverable. Passphrase-based recovery is deferred. The source is present in current `main`, but SAF provider behavior, storage-full handling and real Android Keystore/process-death behavior require runtime testing; no release qualification is established.

The app still has no automatic corruption repair, retained backup, or recovery path for a missing local Keystore key when no valid portable archive/recovery key exists. See [STORAGE_RECOVERY.md](STORAGE_RECOVERY.md) for the local-storage failure contract and recovery boundaries.

The encrypted writer and reader share the same task-list validation: every task must be valid, titles must stay within the 160-character limit, and IDs must be unique. This prevents the writer from persisting a duplicate-ID snapshot that the reader would later reject.

The app's **Demo suggestion** ranking is deterministic local code: open tasks by overdue/nearest due date, then high → medium → low priority for equal dates. It is not an LLM, does not access the network, and does not infer intent. Suggestions are not a downloaded asset.

Clearing app data or uninstalling removes the local task file, attachment payloads, local duplicate-backup history and Keystore keys. Automatic Android backup remains disabled. ### Optional functionality storage and delivery policy (future only)

Optional functionality must not occupy installed storage before the user taps/requests it. These two cases are different:

- **Feature code/resources:** only if separable Android code is justified, use a reviewed, signed dynamic feature module delivered on demand through [Play Feature Delivery](https://developer.android.com/guide/playcore/feature-delivery/on-demand) from an [Android App Bundle](https://developer.android.com/guide/app-bundle). This depends on Google Play distribution; it is not a generic delivery path for a standalone APK or ordinary sideloaded build. Do not fetch executable code from arbitrary remote URLs or run downloaded plugins.
- **Data/model/locale assets:** treat these as data, not code, and fetch only after an explicit user request. Before any transfer show source/provider, license, exact download size, installed-storage impact, network/mobile-data usage, device compatibility, and what removal will clear. Provide visible progress, cancel, retry when offline, integrity/hash verification, and full removal including caches; no pre-tap fetch, background prefetch, auto-update, indexing, or inference.

Future assets require authenticated source metadata (for example, a signed manifest with hashes), integrity checks before use, a reviewed license and compatibility, and private storage. A data pack must not smuggle executable code or be interpreted as code. No module or asset download path is implemented now. Android's [dynamic code loading guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) recommends avoiding dynamic code loading unless needed, warns about tampering/data-exfiltration/code-execution, and notes many remote-loading forms may violate Google Play policies.
