## Standalone GitHub APK updater (release-gated)

The updater code is separate from task storage. It checks only the fixed public [GitHub latest-release endpoint](https://api.github.com/repos/AbrarulHaque8541/ai-personal-task-assistant/releases/latest), at most once per 24 hours from `MainActivity.onResume`, or when the user taps **More → Check now** (which bypasses the interval). It never polls in the background and never includes task contents or history in a request; no app telemetry is implemented. This is not a zero-egress claim: when enabled, the app contacts GitHub for release metadata and, only after download consent, obtains the APK from the GitHub release asset through a bounded allowlist of HTTPS GitHub asset hosts. Metadata checks stay disabled in debug builds and unless the trusted publisher signer is pinned and the updater gate is explicitly enabled. Only `githubSideload` declares `INTERNET` and `ACCESS_NETWORK_STATE`; shared and Play manifests declare no permissions. Neither `REQUEST_INSTALL_PACKAGES` nor a `PackageInstaller` handoff is present.

Before any APK download, the app shows the release name/version/notes and exact declared byte count, then asks for a per-download network choice: **Wi-Fi only (recommended)** is selected by default, or the user may explicitly **Allow mobile data**. The Wi-Fi-only choice is checked before opening each HTTP request and while copying the response; a change away from Wi-Fi stops the download. The user must separately choose **Download and verify**; Cancel starts no APK transfer, and retries are never automatic. After size, hash, package, version, min-SDK, and exact signer checks pass, Daymark offers Android's document picker to save the verified APK to a user-chosen location. The picker suggests a unique `Daymark-v<version>.apk.daymark-pending-<token>.tmp` title, so an empty picker-created document is not a final-looking APK. A compact digest/version/token/name transaction reference is saved in Activity instance state; release metadata and the verified APK stay in the existing app-private recovery record, and no SAF URI or credential is saved. On result, Daymark revalidates the retained artifact, operates only on the returned URI, stages it under `.daymark-incomplete-<token>` before writing, checks size/digest during copy, independently reopens and verifies the destination bytes, and only then requests finalization. If the provider returns the suggested title unchanged, the default name becomes `Daymark-v<version>.apk`; a user-renamed title is preserved. Daymark never resolves or opens an existing document by a guessed name; final-name collision handling is delegated to the provider rename result, and real-provider collision behavior remains unverified (the host fake refuses a collision without changing the existing item). If callback state is missing, Daymark operates only on the exact new URI returned by this `ACTION_CREATE_DOCUMENT` request: it best-effort renames that document to a unique orphan `.tmp` marker and then deletes that exact URI; it never searches for or deletes by display name. If the provider rejects both rename and deletion, cleanup cannot be guaranteed and provider-dependent residue may remain. **Process-death limitation:** If the process dies after the `ACTION_CREATE_DOCUMENT` result but before SAF saving finishes, an incomplete document may remain—under the picker-selected name (normally the suggested `.tmp` title, unless renamed by the user) before staging or the `.daymark-incomplete-<token>` marker once copying starts. The result URI/access grant is not persisted, so automatic resume or guaranteed cleanup is unavailable; residue and cleanup depend on the provider and are unverified on real Android. The verified app-private source remains available for retry or explicit discard. SAF finalization is not guaranteed atomic. Daymark does not open an installer, request install-source access, or install the APK. The user must open a successfully saved file themselves; Android controls any source approval and final confirmation. The current `UpdaterPublisherConfig` gate is false with an empty signer pin, so no updater request or download is operational until protected production signing is configured. Host fake-provider fixtures cover transaction serialization, interruption, finalization, destination read-back, and collision handling; they cannot replace real APK signer parsing or device/provider testing.

### Stable-release publishing prerequisites

1. Publish a non-draft, non-prerelease GitHub Release with one `.apk` asset whose GitHub API `digest` is `sha256:<64 hex characters>`. The version tag must be `vMAJOR.MINOR.PATCH`; the APK `versionName` must match the tag, `versionCode` must exceed the installed app, and the APK application ID must be `com.cue.daymark`.
2. Include this machine-readable block in the release body, followed by human-readable notes. `minSdkVersion` must match the APK manifest and be supported by the device; `signerCertificateSha256` is the APK signing certificate SHA-256 fingerprint.

   ```html
   <!-- daymark-updater-v1
   {"applicationId":"com.cue.daymark","versionCode":2,"minSdkVersion":26,"signerCertificateSha256":"<64 lowercase hex characters>"}
   -->
   ```

3. Configure and protect a publisher release key outside the repository, sign production APKs with it, explicitly enable the sideload updater gate, and pin its actual certificate fingerprint. No production release key or signing setup currently exists; no key is generated or stored in this repository. Debug APKs are signed with a different key and **must never be used as the update target**. Keep the exact same production signer across releases: this updater requires exact certificate continuity and does not implement or verify signing-key rotation lineage. Any rotation must remain fail-closed until separately designed, reviewed, and tested.
4. The owner-selected path is verify/download plus a user-selected save and manual opening. `REQUEST_INSTALL_PACKAGES`, the Android `PackageInstaller` API, and app-launched install-source Settings are not part of this PR. The user—not Daymark—opens the saved APK from Files; Android may require the user to approve the source and confirm installation. Device behavior for that manual route is still unverified.
5. Before offering a saved APK, require the downloaded length and SHA-256 to match GitHub release metadata, and verify package ID, version name/code, min SDK, and signer SHA-256 against both release metadata and the running app. Recheck size and digest while copying to the user-selected document; any mismatch fails closed. Never ask the user to uninstall to force an update.

Daymark stores tasks encrypted with an Android Keystore key. Uninstalling clears that file/key, and changing the app's signing identity can make an update impossible or risk loss of access to encrypted local tasks. Preserve the same production signing identity across releases, and **do not uninstall Daymark as a workaround**. No stable release APK or release signing key is currently available; no release has been published.

## V1 experience

- **Simple path (default):** the first screen asks “What do you want to get done?”, gives an everyday example, and offers an editable text field with a one-tap Add action. A new quick-added task starts with no due date and medium priority; that default is stated on screen. **Add with a date or priority** opens the same editable task form with the draft filled in.
- **Power path:** an explicit top-bar switch reveals title search, All / Today / Upcoming / Completed filters, and deterministic Demo suggestions. It uses the **same task records** as Simple; changing paths does not copy, transform, or hide stored data.
- Both paths support task edit, completion, and deletion. Deletion asks first and can be undone for seven seconds. The task editor has Cancel and system Back behavior.
- Local status is visible. Text entry and date/priority remain editable before saving; a visible message explains the next step after a quick add.

## Accessibility and settings

The app uses native Android controls, descriptive TalkBack labels, scrollable content, keyboard/IME submission, and touch targets of at least 48 dp for primary actions, filters, task controls, and search clearing. **More** provides device/light/dark appearance, Compact/Standard/Extra large app text, a high-contrast palette, permission status, and technical details.

Language is **English-only UI** in this prototype; dates use the device locale. Other translations and right-to-left review are not complete. The screen-reader item points to native Android/TalkBack support; it does not replace Android's accessibility settings. V1 has no custom looping/auto-playing motion, so Android system reduced-motion behavior applies to platform UI; there is no separate in-app reduced-motion switch.

## Local-only operation and content policy

The shared `main` manifest and `play` flavor declare **no permissions**, including `INTERNET`; task flows need no permission and remain local. Only the optional GitHub sideload distribution adds `INTERNET` and `ACCESS_NETWORK_STATE` for its foreground updater. It never uploads task data/history and has no background poller. It declares neither `REQUEST_INSTALL_PACKAGES` nor an app-driven installer path. The publisher gate currently disables updater requests and APK transfer. There is no provider account, sync service, background inference, or model/locale/plugin downloader. The task UI and task records are designed to work offline, including airplane mode; that behavior still requires on-device runtime testing before being called verified.

**More → Permission status** reads the installed app's declared permission list; task capture, edits, completion, deletion, and encrypted storage need none. The `githubSideload` distribution declares updater-only `INTERNET` and `ACCESS_NETWORK_STATE`; `play` declares none. This screen is read-only: it does not request, grant, manage, revoke, or automatically enable access. A full permission center is a proposed/deferred UI, not present in the current source. The updater never requests `REQUEST_INSTALL_PACKAGES`; Android—not Daymark—controls any approval when a user manually opens a saved APK. If a future feature needs protected access, explain why and request only the minimum when the user chooses that feature; runtime permissions require the Android system prompt and the user's decision, while special app access must be granted by the user in Android Settings. If access is denied, keep the rest of the offline app usable, explain the affected feature without repeated pressure, and offer the applicable Settings route for revocation or reconsideration. An ordinary app cannot silently grant itself arbitrary system-level access or bypass the platform's privileged/signature-only grant rules. Do not describe an “autopilot” that requests or accepts everything ([Android permissions overview](https://developer.android.com/guide/topics/permissions/overview), [runtime requests](https://developer.android.com/training/permissions/requesting), [special access](https://developer.android.com/training/permissions/requesting-special), [manifest protection levels](https://developer.android.com/guide/topics/manifest/permission-element)).

Make the app UI itself usable with TalkBack and other accessibility tools; do not request `AccessibilityService` as a generic permission or plugin workaround. Android positions that service for assistive technology, and broad event monitoring can be resource-intensive. Keep it deferred unless a concrete assistive use case is approved, then require separate user opt-in, security review, and device testing ([AccessibilityService guidance](https://developer.android.com/guide/topics/ui/accessibility/service)).

**No optional content ships in V1:** no GGUF weights, voice/language packs, compiled inference runtime, plugin packs, bundled demo content, or other model artifacts. The app's small vector launcher icon is UI chrome, not an optional pack. Optional pack sizes are **N/A (none exist)**. A base release APK target of **<15 MB** remains unmeasured until a genuine release build; no release APK has been built, so do not estimate or claim its size. A debug APK exists but is not eligible for this target.

The app performs ordinary foreground UI, file, and Keystore work while open, so literal zero device load is impossible. It has no app-owned background task, polling, or inference. The updater's source check is foreground/manual only and remains disabled in this build because the publisher installation gate is false; the Play flavor also has no `INTERNET`. Near-zero idle/background work is a design target, not a measured battery claim.

## Task storage and demo suggestions

Task records use schema-versioned JSON encrypted in `files/tasks.enc` with AES-GCM and an AES key kept by Android Keystore. The key is non-exportable; secure-hardware backing depends on the device. Disk and cryptographic operations run on one background executor. A malformed file, unavailable key, or authentication/schema failure leaves the existing file untouched and disables edits. Saves use a temporary file and replacement; failed saves restore the last saved in-memory snapshot and pause further edits.

The app's **Demo suggestion** ranking is deterministic local code: open tasks by overdue/nearest due date, then high → medium → low priority for equal dates. It is not an LLM, does not access the network, and does not infer intent. Suggestions are not a downloaded asset.

Clearing app data or uninstalling removes the local task file/key. Automatic backup is disabled; there is no export, cloud sync, or cross-install migration. Theme and accessibility preferences are non-sensitive ordinary app preferences.

## Deliberately not implemented

- No voice capture, push-to-talk, speech provider, microphone permission, or transcript creation. A future voice feature must request permission only when used, disclose any off-device audio processing, and let the user edit/review the transcript before a task is created.
- No on-device model/GGUF loader, model download, inference, language pack, plugin/CLI/Termux bridge, or hot reload. The standalone APK updater is described above and remains non-operational until permission and publisher-signing gates are resolved.
- No `AssistantProvider`, remote-provider router, or Telegram connection ships in V1. Selection, disclosure, credential, and hosted-service requirements are documented in the deferred integration section below.
- No fake download, model, voice, or plugin controls are present. Future optional content must require an explicit tap; show exact source, license, verified size, device/storage impact; support progress, cancel, resume, hash check, and complete removal of asset plus cache; never download, update, index, or infer in the background; and unload after a user-requested inference.

Never log prompts or keys. Encrypt user-supplied keys under Android Keystore when held on-device, or use protected server-side secret storage for hosted services; never place credentials in app source, an APK, or a public repository.
