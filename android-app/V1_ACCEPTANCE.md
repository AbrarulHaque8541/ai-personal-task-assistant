# Daymark Android V1 acceptance checklist

This is a release checklist, not a claim that every device-level item has already passed. Source-only status is distinguished from runtime verification.

## Original specification: requirement status map

The original platform specification remains the baseline. This map separates current Daymark behavior from future proposals and tests that still require a device.

### Optional capability delivery: storage and security gate (future-only)

- [x] **No pre-tap storage use:** optional feature code, model weights, localization packs and other optional assets must not be downloaded or installed before the user explicitly requests that capability. No silent prefetch, auto-update, indexing or background inference.
- [x] **Code and data are different delivery paths.** If a future feature genuinely needs separable Android code/resources, prefer a signed, reviewed dynamic feature module delivered through **Play Feature Delivery** from an **Android App Bundle**. This requires distribution through Google Play; it is not a generic mechanism for standalone APK/sideload distribution. It must be on-demand, not install-time, and the app needs a no-Play/unavailable fallback. See [Configure on-demand delivery](https://developer.android.com/guide/playcore/feature-delivery/on-demand) and [Android App Bundles](https://developer.android.com/guide/app-bundle).
- [x] Optional model/locale/data assets are data, not downloaded executable code. Fetch them only after an explicit tap. Before starting, show source/provider, license, exact download and installed-storage impact, network/mobile-data use, device compatibility and retention/removal behavior. Do not fetch on startup or before the request.
- [x] For future assets, verify trusted-source provenance and a signed/otherwise authenticated manifest plus cryptographic hashes before use; constrain parsers, verify compatibility/license, store in app-private storage, and support progress, cancellation, retry after no network, and complete user-requested removal including caches. No asset may contain or load arbitrary executable code.
- [ ] Test that a clean install performs no optional download, airplane-mode/no-network behavior, size/network/storage disclosure, progress/cancel/retry/remove, integrity-failure handling, and Play module unavailable/unsupported paths. These optional delivery capabilities are not implemented or tested now.

Android's [dynamic code loading security guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) says to avoid dynamic code loading unless necessary, warns that remote sources create tampering/data-exfiltration/code-execution risks and notes that many remote-loading approaches violate Google Play policy. Do not use arbitrary remote executable code or plugins as a substitute for reviewed store-delivered modules.

## In-app updater release gate

- [x] Source queries only the fixed public GitHub `releases/latest` URL and accepts only a non-draft, non-prerelease newer release. Metadata is bounded and must include one APK asset, GitHub's SHA-256 digest, the Daymark application ID, version code, min SDK, and publisher signer fingerprint. No task/history payload, provider, or telemetry code is attached.
- [x] Checks are called from app foreground (`onResume`) and the explicit **More → Check now** action; persisted wall-clock throttling is 24 hours, and manual check bypasses it. There is no worker, receiver, service, or background polling. Source gates remain closed until the production signer is configured.
- [x] The user must choose **Wi-Fi only (recommended)** (default) or **Allow mobile data**, then separately press **Download and verify**. Wi-Fi-only is enforced before HTTP requests and during transfer; pre-transfer or in-transfer cancellation stops the operation, and retries are not automatic.
- [x] Download/verifier core uses dedicated app-private `noBackupFilesDir` storage, avoiding OS cache eviction and Android backup, with exact expected/actual byte bounds, SHA-256, package/version/minSdk inspection, and release/running/configured signer equality. Before transfer, the release expectations are recorded outside task data; after verification the filename is digest-addressed. On restart, the retained APK is revalidated against the stored digest, package, version, minSdk, installed signer, and publisher signer before it is offered. Unverified bytes use a strict `.partial` staging name; startup cleanup removes only those named partial files in the updater subdirectory. At most one APK (up to 100 MiB) is retained without automatic expiry until explicit discard, including after a user-selected copy is saved; another update cannot replace it until discard. Legacy/orphan files without readable expectations are not offered for saving/opening and require explicit discard. The user must open a saved APK themselves. Daymark does not invoke Android's installer or install-source Settings.
- [x] Permission scope is flavor-specific: shared/Play manifests declare none; `githubSideload` declares `INTERNET` and `ACCESS_NETWORK_STATE`. `REQUEST_INSTALL_PACKAGES` is absent. Publisher updater config defaults disabled and has no real certificate fingerprint.
- [ ] On devices, test the Wi-Fi-only gate, mobile-data choice, process-death/restart recovery and explicit discard, document picker save/cancel/error paths, opening the saved APK from Files, and Android's source approval/final confirmation. The real APK signer parser, system Settings/PackageInstaller UI, and device installation have not been validated.
- [ ] Before publishing, configure an external protected release signing key and pin its SHA-256 fingerprint; publish no APK until the APK's package ID/version/versionCode/minSdk/hash/signer match release metadata and the running app. Never use the debug key or tell users to uninstall to work around a signing mismatch.
- [ ] Test live stable/no-release/prerelease/draft, offline, rate-limit, malformed metadata, cellular consent, cancel, retry, verified install approval, and rollback/update behavior on supported Android devices. GitHub has no releases today; no release APK is signed, installed, or published.

### Release metadata required by the updater

Create a non-draft, non-prerelease GitHub Release with a `vMAJOR.MINOR.PATCH` tag, exactly one `.apk` asset whose release API `digest` is `sha256:<64 hex characters>`, and the following body block followed by human-readable release notes. The tag-derived `versionName` and block `versionCode` must match the APK; `minSdkVersion` and `applicationId` must match its manifest. The SHA-256 signer value is the production APK certificate fingerprint, not the debug certificate.

```html
<!-- daymark-updater-v1
{"applicationId":"com.cue.daymark","versionCode":2,"minSdkVersion":26,"signerCertificateSha256":"<64 lowercase hex characters>"}
-->
```

**Data-loss warning:** Daymark tasks are encrypted using a key held in Android Keystore. Uninstalling removes the encrypted task file/key; a changed signing identity can block an update or make local encrypted data inaccessible. Keep the production signing certificate stable across releases and never recommend uninstalling as an update workaround. Daymark does not request `REQUEST_INSTALL_PACKAGES`, open install-source Settings, or start Android's installer. If the user opens a saved APK manually, Android—not Daymark—controls any source approval and final confirmation; those device screens remain untested.

Run available source checks from the repository root:

```sh
sh ./tools/check-v1-source.sh
```

## User-flow acceptance (device/emulator required)

1. **Simple capture:** first screen asks “What do you want to get done?” and shows the school-trip example. Add a valid title with the keyboard action and button. Blank input is rejected; title can be edited before save. Quick add says it creates medium priority/no due date and shows the next step.
2. **Detailed capture/edit:** choose Add with a date or priority; verify the typed draft is prefilled, due date can be selected/cleared, and priority is Low/Medium/High. Cancel or system Back leaves the existing list unchanged. Edit a saved task and verify its ID/created time remain stable.
3. **Power path parity:** switch to Power and verify exactly the same tasks and completion states are present. Search, All/Today/Upcoming/Completed, and Demo suggestions work. Add/edit in Power, switch back to Simple, and verify the same saved data remains visible.
4. **Complete/delete/cancel/undo:** complete and uncomplete a task. Delete shows a clear confirmation; Keep task cancels without changes. Confirm Delete, then Undo within seven seconds and verify task, due date, priority, and completion state return. Relaunch and verify the final state persists.
5. **Offline:** enable airplane mode before first launch; create, edit, search/filter, complete, delete/undo, force-stop/relaunch, and verify the local task file. Core task flows must never send task data/history. In `githubSideload`, verify updater metadata is checked only in foreground/manual use, an explicit Wi-Fi/mobile choice is shown before APK transfer, and no download begins until **Download and verify** is chosen.
6. **Keyboard and focus:** operate capture, mode switch, search, dialogs, selection controls, and buttons using keyboard/focus navigation; verify visible focus order and Enter/IME actions. Verify Android Back/Cancel discards an unsaved edit and does not create a task.
7. **Text size and contrast:** check system font scaling and app Compact/Standard/Extra large. Check Standard and high-contrast palettes in light, dark, and system-following appearance. Confirm layouts scroll without clipped actions and text remains readable.
8. **TalkBack:** traverse every field/action with TalkBack. Confirm the task-specific completion, edit/delete, mode switch, search-clear, date/priority and storage-status labels are understandable and that dialogs announce their title/actions. Make the app itself accessible; do not ask for `AccessibilityService` as a generic permission/plugin workaround. Any future AccessibilityService needs a concrete assistive use case, separate opt-in/security review and device testing; broad event monitoring can be resource-intensive.
9. **Non-English locale:** test at least one non-English locale and an RTL locale. Dates/numbers currently follow device locale, but app strings remain English only; therefore **full non-English/RTL support is not accepted yet**. Translate every user-facing string and accessibility label, then repeat flows 1–8 before claiming support.
10. **Simple language:** review with nontechnical users; verify the quick-add default, date/priority editor, save status, next step, cancel, confirmation, and Undo are understood without technical guidance.
11. **Permission status (device check unrun):** open More → Permission status and verify it is read-only and core task flows remain usable. Confirm shared/Play declare no permissions and `githubSideload` declares only `INTERNET` plus `ACCESS_NETWORK_STATE`; confirm there is no `REQUEST_INSTALL_PACKAGES` prompt or app-driven install Settings flow.

## Portable encrypted backup acceptance (current stacked source)

- [x] Source provides a pathless bounded binary `.dmbackup` format (not ZIP), fixed magic/version/suite, random backup ID, a 110 MiB whole-archive actual-stream cap, a 10,000-task cap, and attachment caps of 20 MiB/file, 100 MiB aggregate, 100 total and five/task. The parser enforces manifest-declared payload bounds before staging, then authenticates exact streamed record lengths; AES-256-GCM uses full tags, HKDF-SHA-256 per-record keys, unique nonces, authenticated canonical headers/task associations/lengths, and complete manifest/record-set validation.
- [x] Task text, attachment names, MIME types and contents are encrypted. The UI explicitly discloses the visible format/version, backup ID, record type/count, exact attachment sizes and opaque association tokens.
