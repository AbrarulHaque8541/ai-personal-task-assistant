# Offline reminder platform notes

Checked 2026-10-06 against the current Android developer documentation. This codebase currently uses `minSdk 26`, `targetSdk 35`, and the already-installed API 35 toolchain. This source-only review does not change the SDK target or require API 36; API 36 is a Play-submission target requirement, not a blocker for a GitHub review/sideload, so no API 36 work is planned here.

## Alarms and exact access

Android describes exact alarms as time-sensitive user-facing interruptions and recommends inexact alarms whenever they meet the use case. `setExact()` can be delayed by battery-saving measures. `setExactAndAllowWhileIdle()` can run in Doze but spends more device resources. The implementation uses `setExactAndAllowWhileIdle()` only when the user-granted special access is available; otherwise it uses `setAndAllowWhileIdle()` and reports inexact timing. It does not use `setAlarmClock()`, a foreground service, a wake lock, or recurring work. Android still controls delivery; no exact-time promise is made.

On Android 14 and higher, fresh installs targeting Android 13 or higher generally do not receive `SCHEDULE_EXACT_ALARM` by default. Android directs apps to check `canScheduleExactAlarms()`, request the Settings access in the context of a user action, check again after return, and degrade gracefully if the user declines. `USE_EXACT_ALARM` is automatically granted but has limited use cases and Google Play policy implications, so this feature uses the user-granted `SCHEDULE_EXACT_ALARM` instead. Android documents that revoking `SCHEDULE_EXACT_ALARM` stops the app and cancels future exact alarms, and that the permission-state broadcast is sent on grant but not revocation. The exact path therefore also schedules a distinct inexact allow-while-idle backup for nine minutes after the chosen deadline; both alarm paths share encrypted pending/delivered state and cancel each other. This reduces loss after later revocation but remains best-effort under Doze and requires physical-device verification. The fallback is omitted only if a later alarm time cannot fit in the signed epoch-millisecond range; the exact target itself is not silently clamped.

Sources: [Schedule alarms](https://developer.android.com/develop/background-work/services/alarms), [Android 14 exact-alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms), [Request special permissions](https://developer.android.com/training/permissions/requesting-special), [Google Play exact-alarm policy link referenced by Android](https://support.google.com/googleplay/android-developer/answer/12253906).

## Notifications and sound

For target/API 33+, notifications are off by default for new installs until `POST_NOTIFICATIONS` is granted. Android recommends asking in context after a user action; a denial blocks ordinary notifications. Daymark asks only when a user saves a reminder. A denied notification permission means the reminder is not created, while task use remains available.

Android notification-channel sound is set before the channel is submitted. Channels persist, and user-controlled channel changes must be respected. Android also recommends a stable sound URI. Daymark creates a channel ID from the selected sound URI and never rewrites an existing channel; choosing a different sound selects a distinct channel. Android's `ACTION_RINGTONE_PICKER` returns the selected URI, the system default URI, or `null` for Silent. The reminder form requests notification sounds only and does not request audio-storage read access.

Sources: [Notification runtime permission](https://developer.android.com/develop/ui/views/notifications/notification-permission), [NotificationChannel API](https://developer.android.com/reference/android/app/NotificationChannel), [RingtoneManager API](https://developer.android.com/reference/android/media/RingtoneManager).

## Doze and restoration

Doze defers standard alarms, jobs, and syncs. Android's Doze guide says `setAndAllowWhileIdle()` and `setExactAndAllowWhileIdle()` cannot fire more than once per nine minutes per app. The broader `AlarmManager` reference says idle intervals may be significantly longer (for example, about 15 minutes) and the system may reschedule allow-while-idle alarms out of order. The nine-minute rule is a frequency limit, not a delivery promise. The UI states that Android may delay delivery.

Android documents boot, wall-clock change, date change, and time-zone change as standard broadcast actions. The private receiver reloads encrypted reminders and restores pending one-shot alarms. Date/time reminders persist their selected epoch instant, IANA zone, and UTC offset; a device-zone change re-arms the same instant and does not reinterpret the user's selection. Relative timers preserve their stored epoch deadline. Daymark uses Java `ZoneRules.getValidOffsets`: a spring-forward gap has no candidate and is rejected; a fall-back overlap requires a user to select the first or second occurrence, with the UTC offset visible in the choice and saved summary. The selected preview candidate supplies the exact trigger instant, so the displayed local value and offset identify the same instant the alarm receives.

Date/time reminders are supported from a valid future selection through December 31, 2100, inclusive. The date picker, policy validation, encrypted record validation, acceptance checklist, and host tests share this explicit supported limit; values outside it are rejected with clear validation rather than described as unbounded. The selected instant, IANA zone, and UTC offset are persisted; later zone changes do not reinterpret the selection to preserve its wall-clock display. Relative timers preserve their saved instant deadline. Conversion overflow is also rejected rather than wrapped.

Notification delivery uses a durable state protocol: arm the inexact repeating retry before the one-shot alarm, persist `deliveryPending`, post with a stable task-and-generation notification key, then persist `delivered` before retiring the retry. If the process stops before posting, restart reconciliation posts the pending item. If it stops after `notify()` but before the delivered write, retrying the same key replaces that notification instead of creating a duplicate. A process-wide lock serializes receiver delivery, replacement, and cancellation. Cancellation persists a versioned tombstone and arms cleanup before canceling that generation's alarms/notification; stale cleanup cannot cancel a newer generation's notification. During v2-to-v3 reconciliation, the old task-only notification key is also retired before a migrated pending post is replayed. Host tests model each crash window and both cancel/recovery orders; physical Android process-stop and AlarmManager/NotificationManager behavior remains to be checked.

Sources: [Optimize for Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby), [AlarmManager API](https://developer.android.com/reference/android/app/AlarmManager), [Intent standard broadcast actions](https://developer.android.com/reference/android/content/Intent), [Java ZoneRules](https://docs.oracle.com/javase/8/docs/api/java/time/zone/ZoneRules.html), [Java ZonedDateTime](https://docs.oracle.com/javase/8/docs/api/java/time/ZonedDateTime.html), [Java Instant](https://docs.oracle.com/javase/8/docs/api/java/time/Instant.html).

## Retry alarms and date-picker range

Android documents `AlarmManager.setInexactRepeating()` as a repeating alarm with inexact trigger requirements, which can be batched for power efficiency. `INTERVAL_FIFTEEN_MINUTES` is a recognized interval constant (900,000 ms). The Doze guide states that standard alarms are deferred to maintenance windows; this repeating retry is therefore a recovery opportunity, not a punctuality guarantee, and may be delayed while idle. The reminder's one-shot exact/inexact alarm remains the primary delivery path. The retry is armed first and is retained until the delivered-state commit is durable; a primary alarm API failure does not discard an already accepted retry.

The Android `DatePicker.setMaxDate(long)` API takes milliseconds since the epoch in the device's default time zone. Daymark explicitly constrains this picker and its date-time policy to December 31, 2100, rather than implying that the widget's broader representable epoch range is available to users.

Sources: [AlarmManager.setInexactRepeating](https://developer.android.com/reference/android/app/AlarmManager#setInexactRepeating(int,long,long,android.app.PendingIntent)), [AlarmManager interval constants](https://developer.android.com/reference/android/app/AlarmManager#INTERVAL_FIFTEEN_MINUTES), [DatePicker.setMaxDate](https://developer.android.com/reference/android/widget/DatePicker#setMaxDate(long)).

## Verification boundary

Host tests exercise permission fallback decisions, the documented Doze interval, cancellation, snooze, DST gap/overlap choices and invalid persisted offsets, preview-to-trigger identity, the December 31, 2100 date boundary, stable generation-scoped notification identity, each process-death window, tombstone cleanup, and concurrent cancel/recovery ordering. No Gradle build, APK creation, device install, release, merge, API 36 installation, or SDK-license acceptance is part of this change.
