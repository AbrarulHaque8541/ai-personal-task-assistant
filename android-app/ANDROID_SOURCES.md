## Android permission boundaries

Reviewed on 2026-10-05. The current app has no permission declarations or permission-request flows; the references below are for documenting Android's boundaries and any future, feature-specific permission work.

- [Permissions on Android](https://developer.android.com/guide/topics/permissions/overview): distinguishes install-time, runtime, and special permissions; recommends a minimal set, requests associated with the action that needs them, and transparent explanations.
- [Request runtime permissions](https://developer.android.com/training/permissions/requesting): request in context after the user invokes the feature, inspect the user's response, and gracefully degrade on denial. Repeated denial can prevent another system prompt; respect the choice rather than nagging.
- [Request special permissions](https://developer.android.com/training/permissions/requesting-special): special app access is granted by the user through Android Settings, not a runtime permission dialog. Explain before redirecting, then re-check access after the user returns.
- [Manifest `<permission>` element](https://developer.android.com/guide/topics/manifest/permission-element): documents protection levels. A `signature` permission is limited to apps signed with the same certificate as the app that defined it; an ordinary app cannot self-grant arbitrary privileged/system or signature-only access.

## Android background, sandbox, accessibility, and user-space boundaries

Reviewed on 2026-10-05. These sources support the app's least-privilege and low-background boundaries; they do not imply that deferred integrations exist in this project.

- [Background execution limits](https://developer.android.com/about/versions/oreo/background): Android restricts background services and broadcasts for apps idle in the background; scheduled work is system-managed, not a mechanism for promising an always-running daemon.
- [System restrictions on background tasks](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions): background work can be limited by system and user resource restrictions; test behavior under restrictions rather than claiming the app can disable them.
- [Restrictions on starting a foreground service from the background](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start): for apps targeting Android 12/API 31 or higher, background foreground-service starts are restricted except for defined cases; later Android versions also enforce service-type and while-in-use permission conditions.
- [Android application sandbox](https://source.android.com/docs/security/app-sandbox): Android assigns apps separate UIDs and enforces kernel-level process isolation. User-space tools do not grant an ordinary APK root or unrestricted OS access.
- [Accessibility services](https://developer.android.com/guide/topics/ui/accessibility/service): an accessibility service is a specialized assistive service with dedicated manifest declarations and system binding; it is not a generic permission/plugin shortcut or substitute for making this app's own UI accessible. Broad event monitoring can be resource-intensive. Any future service needs a concrete assistive use case and separate user opt-in, security review, and device testing.
- [Special app access](https://developer.android.com/training/permissions/requesting-special): includes drawing over other apps; the user grants special access in Android Settings after an in-context rationale. Such access is not declared or requested by this V1 app.
- [PRoot upstream project](https://proot-me.github.io/): describes PRoot as a user-space implementation of chroot-like behavior that does not require privileges. This does not mean real root/chroot privileges or escape from Android's app sandbox.
- [Termux Android app source](https://github.com/termux/termux-app): the Termux project describes a separate Android terminal application and Linux environment; it is not a bridge implemented by this project. No ADB/Termux integration ships here.

## Accessibility contrast check (2026-10-05)

The project uses WCAG 2.2 Success Criterion 1.4.3 as a text-contrast benchmark: normal text should reach at least 4.5:1 against its background, and computed ratios must not be rounded up to pass ([W3C explanation of Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). This is a useful color benchmark, not a claim that web-content conformance certifies an Android UI.

A source-derived regression test now reads the app's light/dark and standard/high-contrast palette definitions and checks text-role/background pairs. It first found low contrast in normal light-theme muted labels, due-today warnings, and danger labels; those colors were darkened. ## GGUF format and Android inference runtimes (2026-10-05)

- The upstream [GGUF specification](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) defines a binary model format used by GGML-based executors, designed for features including single-file deployment, mmap loading, extensibility, and self-contained model-loading metadata. It is a **format**, not an Android runtime or a guarantee of compatibility; model-weight licensing/provenance is separate.
- The upstream [llama.cpp project](https://github.com/ggml-org/llama.cpp) provides a C/C++ inference runtime with GGUF support and local/cloud use cases, but that repository does not establish compatibility with this app's Android build or validate a specific model's license/performance.
- Google's [MediaPipe LLM Inference Android guide](https://ai.google.dev/edge/mediapipe/solutions/genai/llm_inference/android) documents a local `.task` model path, says its model is too large to bundle in an APK, and marks the API maintenance-only with a recommendation to migrate to LiteRT-LM. Google's [LiteRT-LM Android guide](https://developers.google.com/edge/litert-lm/android) instead documents a local `.litertlm` model path and optional GPU/NPU backends, with engine initialization work kept off the UI thread.
- The reviewed Google Android pages do **not** document direct GGUF ingestion. A future GGUF feature therefore needs either an independently verified GGUF-capable native runtime or an explicitly tested conversion/package path; downloading a `.gguf` alone does not implement inference. No model/runtime/download feature exists in Daymark.

## Dynamic code, plugins, and supportable app updates (2026-10-05)

Android's [dynamic code loading guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) recommends avoiding runtime code loading where possible because it raises tampering/injection risk; it says many remote-code forms may violate Play policy. For apps targeting Android 14/API 34+, [all dynamically loaded files must be read-only](https://developer.android.com/about/versions/14/behavior-changes-14). Daymark therefore has no executable plugin/DEX/JAR/APK downloader or unrestricted shell bridge. A plugin concept should start from a narrow, typed in-process API; actual executables should ship through the reviewed app release, not be silently loaded as downloaded plugins. The sources do not classify every model artifact as executable code; check its real loading behavior rather than assuming an AI exception.

For Android update acceptance, the [official update guide](https://developer.android.com/google/play/app-updates) requires the same application ID, a matching signing certificate (or valid proof-of-rotation), and an equal-or-higher version code. [Play App Signing](https://developer.android.com/studio/publish/app-signing) distinguishes the developer upload key from Google's distribution signing key. Daymark has **no updater or release pipeline today**; the supportable future direction is a signed app release via Google Play or a verified APK channel with stable package/signing identity, not an untested app/OS OTA mechanism. Store delivery does not imply immediate updates: Play availability and user/developer choices still apply.

## Linux/Termux and inter-app bridge limits (2026-10-05)

The upstream [Termux app documentation](https://github.com/termux/termux-app) describes a separate Android terminal/Linux environment and warns that Android 12+ may kill excessive phantom processes and high-CPU processes; it is not a dependable unrestricted background worker. [Termux:API](https://github.com/termux/termux-api) exposes selected Android APIs to Termux command-line programs, but its documented permission model requires the same signing key as the main Termux app and restricts calls to that app. It is not a generic shell bridge available to Daymark.

Android's [application sandbox documentation](https://source.android.com/docs/security/app-sandbox) describes per-app UIDs/processes and isolated app-specific data. A future cross-app integration must be an explicit, narrow IPC feature—not `sh -c`, arbitrary commands, unrestricted file access, or an assumed always-on daemon. Android documents [bound services](https://developer.android.com/develop/background-work/services/bound-services) and component-export/security controls as possible IPC building blocks; verify caller identity, keep components non-exported unless required, enforce a signature/permission or narrow allowlist, accept typed data rather than command strings, and request any needed permission only after the user initiates that feature. Those implementation checks are roadmap requirements, not current functionality; V1 has no plugin, Termux, CLI, service bridge, or shell execution.

For update UX choices, Google's [Play In-app updates guide](https://developer.android.com/guide/playcore/in-app-updates) distinguishes flexible updates—which download/install in the background—from immediate updates, where the active user accepts a full-screen prompt and Play handles the update/restart. Android's [`PackageInstaller`](https://developer.android.com/reference/android/content/pm/PackageInstaller) can stage a signed APK session, but commit can return `STATUS_PENDING_USER_ACTION`; silent completion is documented for device/profile-owner cases, not ordinary consumer apps. Given this project's no-auto-download/explicit-action policy, any future in-app update prompt must clearly identify the signed app update and wait for the user to start it; do not claim the app can suppress Play's own update settings or silently install from an ordinary APK.

## Current platform, local AI, storage, accessibility, and locale findings (2026-10-05)

**Platform and release target.** Google's [target API requirement](https://developer.android.com/google/play/requirements/target-sdk) states that, beginning **2026-08-31**, new apps and app updates submitted to Google Play must target **Android 16 / API 36 or higher** for ordinary mobile apps, with listed form-factor/private-app exceptions. This project currently builds with `targetSdk 35`, and its pinned AGP 8.8.2 is documented in the [AGP 8.8 release notes](https://developer.android.com/build/releases/agp-8-8-0-release-notes) as supporting at most API 35. The current debug build is therefore **not Play-submission-ready**; upgrading the SDK/AGP target and running API 36+ compatibility tests is a release blocker.

The official [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16) say the edge-to-edge opt-out is deprecated and disabled for apps targeting API 36 on Android 16; the [Views edge-to-edge guide](https://developer.android.com/develop/ui/views/layout/edge-to-edge) says Android 15+ already displays target-35+ apps edge-to-edge and explains system-bar, display-cutout, and gesture insets. Only SDK Platform 35 and Build Tools 35.0.0 are installed in this environment, so API 36 was not built or tested. Treat target-36 migration and runtime checks for bars, cutouts, IME/keyboard, dialogs, rotation, navigation modes, and large text across API 35/36 as a release gate, not a current capability claim. Android's [process-lifecycle guidance](https://developer.android.com/guide/components/activities/process-lifecycle) also makes clear that process lifetime is system-controlled and `onDestroy()` is not guaranteed after process death, so the app must not depend on a persistent background process.

**Optional on-device AI.** [Gemini Nano](https://developer.android.com/ai/gemini-nano) runs inside Android AICore and is exposed through the [ML Kit GenAI APIs](https://developers.google.com/ml-kit/genai), rather than as weights bundled by an app. Availability is device/model-specific, quotas apply, and inference is restricted to the top foreground app. The [Prompt API](https://developers.google.com/ml-kit/genai/prompt/android/get-started) exposes `AVAILABLE`, `DOWNLOADABLE`, `DOWNLOADING`, and `UNAVAILABLE` status, while AICore manages model distribution/updates through a system path that may involve Private Compute Services. This is not a promise that the operating system never downloads or updates a model. Daymark has no AICore integration; before considering one, decide whether system-managed model downloads fit the product's strict user-started-download rule, provide status/unavailable handling, and never cloud-fallback silently.

**Local data and backup.** Android's [Keystore guidance](https://developer.android.com/privacy-and-security/keystore) describes non-exportable keys, but hardware-backed protection is conditional and Keystore does not encrypt files by itself; the app still needs an authenticated-encryption implementation and device testing. [Auto Backup](https://developer.android.com/identity/data/autobackup) is on by default for many app-private data classes and can include internal files, preferences, and databases; its documentation notes an Android 12+ device-to-device transfer caveat on some manufacturers even when `allowBackup=false`. Daymark currently uses an AES-GCM encrypted app-private JSON store, not Room/SQLCipher, and declares backup disabled. Verify any stronger “device-only/no-transfer” promise against data-extraction rules and real-device restore/transfer behavior; Keystore invalidation, migration, recovery, and hardware backing remain untested on a device.

**Accessibility and localization.** Android's [accessibility-service guide](https://developer.android.com/guide/topics/ui/accessibility/service) documents selected event types, optional UI-tree inspection and gesture capabilities, and warns broad `typeAllMask` can be resource-intensive; it is not a generic plugin or model runtime. Google's [TalkBack overview](https://support.google.com/accessibility/android/answer/6283677?hl=en) notes that behavior varies by manufacturer, Android release, and TalkBack version. The app should make its own controls accessible rather than request an AccessibilityService without a real assistive use case. Android 13+ [per-app language settings](https://developer.android.com/guide/topics/resources/app-languages) display locales the app actually supports; [localization guidance](https://developer.android.com/guide/topics/resources/localization) requires the app to ship translated resources. Daymark is currently English-only; the new checks are source assertions, not TalkBack, translated-flow, RTL, or rendered-layout tests.

**Provider separation.** The official [DeepSeek API docs](https://api-docs.deepseek.com/) describe a hosted, API-keyed network service; the [DeepSeek Harness repository](https://github.com/deepseek-ai/deepseek-harness) identifies itself as developer preview and does not establish Android support or a no-shell local runtime. xAI's [Grok API](https://docs.x.ai/overview) is a hosted HTTPS service; the distinct [Grok-1 open-weight repository](https://github.com/xai-org/grok-1) describes a 314B JAX release, not evidence that current hosted models run on Android. [Telegram's Bot API](https://core.telegram.org/bots/api) is an HTTPS bot bridge, not inference; it retains pending updates for no longer than 24 hours, and [Telegram's bot overview](https://core.telegram.org/bots) warns that a bot token gives its holder full control. [Alibaba Model Studio](https://www.alibabacloud.com/help/en/model-studio/what-is-model-studio) is a region-specific hosted service; Qwen open weights/local serving are separate, and licensing must be checked for the exact [Qwen model/repository](https://github.com/QwenLM/Qwen3.8). None of these hosted products is integrated; if ever added, each remains explicit opt-in, clearly remote, cost/data disclosed, and independent of the local core.
