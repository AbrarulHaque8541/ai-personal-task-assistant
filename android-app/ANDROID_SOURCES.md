## Android permission boundaries

Reviewed on 2026-10-06 against main `66476cb49a6caa9a43b65db39912ee397b6e6857`. The shared manifest declares normal `INTERNET`; the Play flavor inherits it, and the `githubSideload` flavor additionally declares `ACCESS_NETWORK_STATE` for the gated updater. There is no runtime permission request, `REQUEST_INSTALL_PACKAGES`, or app-driven install-source Settings flow. The references below document Android's boundaries and future, feature-specific permission work.

The current app declares only normal `INTERNET` in its shared manifest; task CRUD needs no permission. The merged sideload variant also contains `ACCESS_NETWORK_STATE`. No runtime permission requests or special-access flows are implemented.

- [Permissions on Android](https://developer.android.com/guide/topics/permissions/overview): distinguishes install-time, runtime, and special permissions; recommends a minimal set, requests associated with the action that needs them, and transparent explanations.
- [Request runtime permissions](https://developer.android.com/training/permissions/requesting): request in context after the user invokes the feature, inspect the user's response, and gracefully degrade on denial. Repeated denial can prevent another system prompt; respect the choice rather than nagging.
- [Request special permissions](https://developer.android.com/training/permissions/requesting-special): special app access is granted by the user through Android Settings, not a runtime permission dialog. Explain before redirecting, then re-check access after the user returns.
- [Manifest `<permission>` element](https://developer.android.com/guide/topics/manifest/permission-element): documents protection levels. A `signature` permission is limited to apps signed with the same certificate as the app that defined it; an ordinary app cannot self-grant arbitrary privileged/system or signature-only access.

## Embedded browser boundaries

The app uses Android System WebView, not a bundled engine or Custom Tab. Android's [WebView integration guide](https://developer.android.com/develop/ui/views/layout/webapps/webview) describes embedding web content in an Activity; [`WebSettings`](https://developer.android.com/reference/android/webkit/WebSettings) documents JavaScript, Safe Browsing, mixed-content, file-access, network-blocking, and window settings. Daymark enables JavaScript for normal site compatibility without adding a JavaScript-to-native bridge, defaults Safe Browsing on, blocks mixed content, and disables file/content access. Browser Settings offers an explicit warning-confirmed, locally persisted Safe Browsing opt-out; Daymark applies that preference through `WebSettings.setSafeBrowsingEnabled` to the active and newly created WebViews. The Safe Browsing provider/endpoint remains platform-managed and is not selectable in Daymark; standard Android WebView may use Google/Play Services. Every WebView is constructed with page/resource loads blocked. Only the explicit, disclosure-confirmed Online preference plus a separate Go/site tap releases Daymark page/resource loads; a missing/malformed preference defaults to Offline, and toggling Online alone sends no page request. The app opts out of WebView diagnostic metrics with `android.webkit.WebView.MetricsOptOut=true`. The Online/Offline preference does not control Safe Browsing and Offline does not guarantee zero platform egress.

Android's [WebView Safe Browsing guidance](https://developer.android.com/develop/ui/views/layout/webapps/managing-webview) describes URL verification with Google Safe Browsing. Android also exposes a [Safe Browsing privacy-policy URL](https://developer.android.com/reference/android/webkit/WebView#getSafeBrowsingPrivacyPolicyUrl()) for the platform service. The [upstream Android WebView Safe Browsing notes](https://chromium.googlesource.com/chromium/src.git/+/refs/heads/main/android_webview/browser/safe_browsing/README.md) describe version-dependent URL-hash mechanisms: WebView M126+ can send a partial URL hash through a proxy for real-time checks; earlier versions use a local partial-hash database and may query a server for matching hashes after a prefix match. The platform may use Google/Play Services for threat-list updates or safety checks. These are hash-based checks, not a statement that every full URL is sent; WebView version and device settings affect the method. The provider is not user-selectable in Daymark, even though Browser Settings lets the user enable or disable the Safe Browsing feature for Daymark WebViews. The Online/Offline switch gates only Daymark page/resource loads and does not promise zero platform traffic. Separately, a requested search/page sends its query or URL and ordinary connection data to the selected provider/site, and page resources may contact third-party endpoints that may log requests.

Daymark applies the local user preference through [`WebSettings.setSafeBrowsingEnabled(boolean)`](https://developer.android.com/reference/android/webkit/WebSettings#setSafeBrowsingEnabled(boolean)); disabling requires an explicit in-app protection warning. This controls Safe Browsing in Daymark's WebViews, not independent Android/Google/Play Services activity. The [Safe Browsing privacy-policy API](https://developer.android.com/reference/android/webkit/WebView#getSafeBrowsingPrivacyPolicyUrl()) points to the platform policy; the search engine is user-selectable, but the Safe Browsing provider itself is not.

The [`WebViewClient`](https://developer.android.com/reference/android/webkit/WebViewClient) reference says `shouldOverrideUrlLoading(WebView, WebResourceRequest)` can be called for page/user navigation and HTTP redirects, and returning `true` aborts the current WebView load. It is not called for app-initiated `loadUrl()` or POST requests; Daymark validates app-issued URLs before loading them and rejects non-HTTPS callback destinations. [`WebResourceRequest.isForMainFrame()` and `isRedirect()`](https://developer.android.com/reference/android/webkit/WebResourceRequest) identify frame context and server redirects. The false `usesCleartextTraffic` policy and `MIXED_CONTENT_NEVER_ALLOW` remain independent backstops for cleartext that is not covered by the navigation callback.

Android's [network security configuration guidance](https://developer.android.com/privacy-and-security/security-config#CleartextTrafficPermitted) says cleartext is disabled by default for apps targeting API 28+ and can be enabled at a broad base-config or narrowed to domains. Because this browser accepts arbitrary public sites, no cleartext opt-in or per-site exception is implemented in this branch. HTTPS is used for searches and bare domains; typed HTTP and HTTP redirect/navigation attempts are blocked. A site-specific HTTP exception would need a separate explicit request.

Android's [`WebChromeClient`](https://developer.android.com/reference/android/webkit/WebChromeClient) APIs cover website-origin permission requests and new-window creation; this app denies location and WebView resource permission requests, and rejects pop-up/new-window requests. Download requests are not handed to a download service. `BrowserHistory` stores at most 50 unique validated HTTPS origins (scheme, lowercase host, and non-default port), never a path, query, fragment, URL userinfo, or page title. Legacy serialized entries are normalized to origins on launch; reopening a saved entry opens its origin, while the active WebView continues loading the full validated route/query. [`WebStorage.deleteAllData()`](https://developer.android.com/reference/android/webkit/WebStorage) clears Web SQL and HTML5 Web Storage across the WebView storage managed for the app; [`CookieManager.removeAllCookies()`](https://developer.android.com/reference/android/webkit/CookieManager) removes cookies asynchronously. **Site history & data** also clears the saved origins, local current-WebView history, its resource cache and SSL exception preferences. `WebView.clearFormData()` only dismisses a currently open autocomplete popup; it does not remove data saved by Android Autofill services or password managers. The UI discloses the all-site scope, asynchronous cookie deletion, and these exclusions. None of these local operations erases records held by a remote site/search provider or browser data in other apps.

## Android background, sandbox, accessibility, and user-space boundaries

Reviewed on 2026-10-05. These sources support the app's least-privilege and low-background boundaries; they do not imply that deferred integrations exist in this project.

- [Background execution limits](https://developer.android.com/about/versions/oreo/background): Android restricts background services and broadcasts for apps idle in the background; scheduled work is system-managed, not a mechanism for promising an always-running daemon.
- [System restrictions on background tasks](https://developer.android.com/develop/background-work/background-tasks/bg-work-restrictions): background work can be limited by system and user resource restrictions; test behavior under restrictions rather than claiming the app can disable them.
- [Restrictions on starting a foreground service from the background](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start): for apps targeting Android 12/API 31 or higher, background foreground-service starts are restricted except for defined cases; later Android versions also enforce service-type and while-in-use permission conditions.
- [Android application sandbox](https://source.android.com/docs/security/app-sandbox): Android assigns apps separate UIDs and enforces kernel-level process isolation. User-space tools do not grant an ordinary APK root or unrestricted OS access.
- [Accessibility services](https://developer.android.com/guide/topics/ui/accessibility/service): an accessibility service is a specialized assistive service with dedicated manifest declarations and system binding; it is not a generic permission/plugin shortcut or substitute for making this app's own UI accessible. Broad event monitoring can be resource-intensive. Any future service needs a concrete assistive use case and separate user opt-in, security review, and device testing.
- [Special app access](https://developer.android.com/training/permissions/requesting-special): includes drawing over other apps; the user grants special access in Android Settings after an in-context rationale. Such access is not declared or requested by this V1 app.
- [PRoot upstream project](https://proot-me.github.io/): describes PRoot as a user-space implementation of chroot-like behavior that does not require privileges. This does not mean real root/chroot privileges or escape from Android's app sandbox.
- [Termux Android app source](https://github.com/termux/termux-app): the Termux project describes a separate Android terminal application and Linux environment; it is not a bridge implemented by this project. No ADB/Termux integration ships here.

## GGUF format and Android inference runtimes (2026-10-05)

- The upstream [GGUF specification](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md) defines a binary model format used by GGML-based executors, designed for features including single-file deployment, mmap loading, extensibility, and self-contained model-loading metadata. It is a **format**, not an Android runtime or a guarantee of compatibility; model-weight licensing/provenance is separate.
- The upstream [llama.cpp project](https://github.com/ggml-org/llama.cpp) provides a C/C++ inference runtime with GGUF support and local/cloud use cases, but that repository does not establish compatibility with this app's Android build or validate a specific model's license/performance.
- Google's [MediaPipe LLM Inference Android guide](https://ai.google.dev/edge/mediapipe/solutions/genai/llm_inference/android) documents a local `.task` model path, says its model is too large to bundle in an APK, and marks the API maintenance-only with a recommendation to migrate to LiteRT-LM. Google's [LiteRT-LM Android guide](https://developers.google.com/edge/litert-lm/android) instead documents a local `.litertlm` model path and optional GPU/NPU backends, with engine initialization work kept off the UI thread.
- The reviewed Google Android pages do **not** document direct GGUF ingestion. A future GGUF feature therefore needs either an independently verified GGUF-capable native runtime or an explicitly tested conversion/package path; downloading a `.gguf` alone does not implement inference. No model/runtime/download feature exists in Daymark.

## Dynamic code, plugins, and supportable app updates (2026-10-05)

Android's [dynamic code loading guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) recommends avoiding runtime code loading where possible because it raises tampering/injection risk; it says many remote-code forms may violate Play policy. For apps targeting Android 14/API 34+, [all dynamically loaded files must be read-only](https://developer.android.com/about/versions/14/behavior-changes-14). Daymark therefore has no executable plugin/DEX/JAR/APK downloader or unrestricted shell bridge. A plugin concept should start from a narrow, typed in-process API; actual executables should ship through the reviewed app release, not be silently loaded as downloaded plugins. The sources do not classify every model artifact as executable code; check its real loading behavior rather than assuming an AI exception.

For Android update acceptance, the [official update guide](https://developer.android.com/google/play/app-updates) requires the same application ID, a matching signing certificate (or valid proof-of-rotation), and an equal-or-higher version code. [Play App Signing](https://developer.android.com/studio/publish/app-signing) distinguishes the developer upload key from Google's distribution signing key. **At this 2026-10-05 snapshot**, Daymark had a source-level GitHub sideload release check, consented download, artifact/signer verification, and user-directed file saving for manual APK opening, but the production signer pin and release pipeline had not been established. Those are historical findings, superseded by later release work. The `v1.0.0` GitHub page still has no attached APK asset. `REQUEST_INSTALL_PACKAGES` and app-driven `PackageInstaller` handoff remain absent. The supportable release route remains a signed app release via Google Play or a verified APK channel with stable package/signing identity, not an untested app/OS OTA mechanism. Store delivery does not imply immediate updates: Play availability and user/developer choices still apply.

## Linux/Termux and inter-app bridge limits (2026-10-05)

The upstream [Termux app documentation](https://github.com/termux/termux-app) describes a separate Android terminal/Linux environment and warns that Android 12+ may kill excessive phantom processes and high-CPU processes; it is not a dependable unrestricted background worker. [Termux:API](https://github.com/termux/termux-api) exposes selected Android APIs to Termux command-line programs, but its documented permission model requires the same signing key as the main Termux app and restricts calls to that app. It is not a generic shell bridge available to Daymark.

Android's [application sandbox documentation](https://source.android.com/docs/security/app-sandbox) describes per-app UIDs/processes and isolated app-specific data. A future cross-app integration must be an explicit, narrow IPC feature—not `sh -c`, arbitrary commands, unrestricted file access, or an assumed always-on daemon. Android documents [bound services](https://developer.android.com/develop/background-work/services/bound-services) and component-export/security controls as possible IPC building blocks; verify caller identity, keep components non-exported unless required, enforce a signature/permission or narrow allowlist, accept typed data rather than command strings, and request any needed permission only after the user initiates that feature. Those implementation checks are roadmap requirements, not current functionality; V1 has no plugin, Termux, CLI, service bridge, or shell execution.

For update UX choices, Google's [Play In-app updates guide](https://developer.android.com/guide/playcore/in-app-updates) distinguishes flexible updates—which download/install in the background—from immediate updates, where the active user accepts a full-screen prompt and Play handles the update/restart. Android's [`PackageInstaller`](https://developer.android.com/reference/android/content/pm/PackageInstaller) can stage a signed APK session, but this project deliberately does not use it: after verification Daymark offers a user-selected save location, and the user opens the saved APK themselves. The user must choose Wi-Fi only (default) or explicitly allow mobile data before the separate download consent. Android may require source approval and final confirmation when the saved APK is opened; this device flow remains untested. Do not claim the app can suppress Play's own update settings or silently install from an ordinary APK.

The official [Android 16 behavior changes](https://developer.android.com/about/versions/16/behavior-changes-16) say the edge-to-edge opt-out is deprecated and disabled for apps targeting API 36 on Android 16; the [Views edge-to-edge guide](https://developer.android.com/develop/ui/views/layout/edge-to-edge) says Android 15+ already displays target-35+ apps edge-to-edge and explains system-bar, display-cutout, and gesture insets. At the October 12 local-build snapshot, API 36 debug APKs built; no physical-device runtime or visual acceptance was established. Android's [process-lifecycle guidance](https://developer.android.com/guide/components/activities/process-lifecycle) also makes clear that process lifetime is system-controlled and `onDestroy()` is not guaranteed after process death, so the app must not depend on a persistent background process.

**Optional on-device AI.** [Gemini Nano](https://developer.android.com/ai/gemini-nano) runs inside Android AICore and is exposed through the [ML Kit GenAI APIs](https://developers.google.com/ml-kit/genai), rather than as weights bundled by an app. Availability is device/model-specific, quotas apply, and inference is restricted to the top foreground app. The [Prompt API](https://developers.google.com/ml-kit/genai/prompt/android/get-started) exposes `AVAILABLE`, `DOWNLOADABLE`, `DOWNLOADING`, and `UNAVAILABLE` status, while AICore manages model distribution/updates through a system path that may involve Private Compute Services. This is not a promise that the operating system never downloads or updates a model. Daymark has no AICore integration; before considering one, decide whether system-managed model downloads fit the product's strict user-started-download rule, provide status/unavailable handling, and never cloud-fallback silently.

**Local data and backup.** Android's [Keystore guidance](https://developer.android.com/privacy-and-security/keystore) describes non-exportable keys, but hardware-backed protection is conditional and Keystore does not encrypt files by itself; the app still needs an authenticated-encryption implementation and device testing. [Auto Backup](https://developer.android.com/identity/data/autobackup) is on by default for many app-private data classes and can include internal files, preferences, and databases; its documentation notes an Android 12+ device-to-device transfer caveat on some manufacturers even when `allowBackup=false`. Daymark currently uses an AES-GCM encrypted app-private JSON store, not Room/SQLCipher, and declares backup disabled. Verify any stronger “device-only/no-transfer” promise against data-extraction rules and real-device restore/transfer behavior; Keystore invalidation, migration, recovery, and hardware backing remain untested on a device.

**Accessibility and localization.** Android's [accessibility-service guide](https://developer.android.com/guide/topics/ui/accessibility/service) documents selected event types, optional UI-tree inspection and gesture capabilities, and warns broad `typeAllMask` can be resource-intensive; it is not a generic plugin or model runtime. Google's [TalkBack overview](https://support.google.com/accessibility/android/answer/6283677?hl=en) notes that behavior varies by manufacturer, Android release, and TalkBack version. The app should make its own controls accessible rather than request an AccessibilityService without a real assistive use case. Android 13+ [per-app language settings](https://developer.android.com/guide/topics/resources/app-languages) display locales the app actually supports; [localization guidance](https://developer.android.com/guide/topics/resources/localization) requires the app to ship translated resources. Daymark is currently English-only; the new checks are source assertions, not TalkBack, translated-flow, RTL, or rendered-layout tests.

**Provider separation.** The official [DeepSeek API docs](https://api-docs.deepseek.com/) describe a hosted, API-keyed network service; the [DeepSeek Harness repository](https://github.com/deepseek-ai/deepseek-harness) identifies itself as developer preview and does not establish Android support or a no-shell local runtime. xAI's [Grok API](https://docs.x.ai/overview) is a hosted HTTPS service; the distinct [Grok-1 open-weight repository](https://github.com/xai-org/grok-1) describes a 314B JAX release, not evidence that current hosted models run on Android. [Telegram's Bot API](https://core.telegram.org/bots/api) is an HTTPS bot bridge, not inference; it retains pending updates for no longer than 24 hours, and [Telegram's bot overview](https://core.telegram.org/bots) warns that a bot token gives its holder full control. [Alibaba Model Studio](https://www.alibabacloud.com/help/en/model-studio/what-is-model-studio) is a region-specific hosted service; Qwen open weights/local serving are separate, and licensing must be checked for the exact [Qwen model/repository](https://github.com/QwenLM/Qwen3.8). None of these hosted products is integrated; if ever added, each remains explicit opt-in, clearly remote, cost/data disclosed, and independent of the local core.

### Android 16, Play policy, and idle work

Android 16 is API 36. For ordinary mobile apps, Google Play's [target API requirement](https://developer.android.com/google/play/requirements/target-sdk) took effect on **2026-08-31** for new submissions and updates. Android's [API-36 target changes](https://developer.android.com/about/versions/16/behavior-changes-16) include removal of the edge-to-edge opt-out on Android 16, predictive-back behavior, large-screen orientation/resizability changes, and scheduling behavior; [all-app changes](https://developer.android.com/about/versions/16/behavior-changes-all) also alter JobScheduler quotas affecting WorkManager, JobScheduler, and DownloadManager. The October 12 local debug build used AGP 8.8.2 and emitted a compileSdk-35 support warning; that toolchain warning is historical and superseded by the October 13 current-source correction above. Physical Android 16 runtime and visual checks remain open; follow the device matrix before a production build.

Android recommends bounded, constrained, batched scheduled work and cautions against unnecessary persistent processes/foreground services. [Doze/App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) defer background CPU, network, jobs, syncs, and alarms; Android 16 may stop work under system/thermal/resource conditions. No polling, persistent socket, wake lock, automatic model download, or background inference should be added to the core.

### Storage, permissions, keys, and accessibility/locales

AOSP's [application sandbox](https://source.android.com/docs/security/app-sandbox) gives apps distinct UIDs and kernel-enforced isolation. Android says to request only necessary permissions, in context after the user invokes the feature, and degrade gracefully after denial ([permission overview](https://developer.android.com/guide/topics/permissions/overview), [runtime requests](https://developer.android.com/training/permissions/requesting)). [Keystore](https://developer.android.com/privacy-and-security/keystore) makes key material non-exportable and may use secure hardware, but hardware backing is device/algorithm-dependent; a compromised app/OS may still use an authorized key. Android warns that [hardcoded secrets are recoverable](https://developer.android.com/privacy-and-security/risks/hardcoded-cryptographic-secrets) and [sensitive values should not be logged](https://developer.android.com/privacy-and-security/risks/log-info-disclosure). [Auto Backup](https://developer.android.com/identity/data/autobackup) can include app files, preferences, and databases by default for eligible apps, so device-local data requires a deliberate backup/D2D policy. Daymark currently uses app-private AES-GCM JSON, not Room/SQLite; no hardware-backed Keystore or restore behavior was device-tested in this review.

Android accessibility guidance recommends scalable `sp` text (including nonlinear scaling up to 200%), at least **4.5:1** contrast for small text and **3:1** for larger text, and **48dp** touch targets. Meaningful labels/roles and manual [TalkBack plus automated/user testing](https://developer.android.com/guide/topics/ui/accessibility/testing) are complementary; source checks cannot establish rendered or spoken behavior. This branch's palette source test measures 5.00:1 minimum, but actual contrast, TalkBack, font rendering, and touch targets remain device NOT TESTED. Android [per-app languages](https://developer.android.com/guide/topics/resources/app-languages), [locale-aware resources](https://developer.android.com/guide/topics/resources/localization), [`DateTimeFormatter`](https://developer.android.com/reference/java/time/format/DateTimeFormatter), [pseudo-locales](https://developer.android.com/guide/topics/resources/pseudolocales), and [RTL layout guidance](https://developer.android.com/training/basics/supporting-devices/languages) support a resource-based, offline localization path. Daymark is English-only; translation, en-XA/ar-XB, RTL, and locale UI rendering are not verified here.

### On-device AI, GGUF, and future model downloads

Google's [ML Kit GenAI overview](https://developers.google.com/ml-kit/genai) and [Prompt API guide](https://developers.google.com/ml-kit/genai/prompt/android/get-started) describe local Gemini Nano inference through AICore, but device/model availability and status must be checked, quotas and token limits apply, and calls are allowed only while the app is top/foreground. AICore manages model distribution/updates through system services; the reviewed docs do not identify an app switch guaranteeing that every system model transfer is user-started. Do not adopt this path until its managed-download behavior fits the product's explicit-consent requirement. [LiteRT-LM](https://developers.google.com/edge/litert-lm/android) is a separate local `.litertlm` pipeline. Official [llama.cpp Android docs](https://github.com/ggml-org/llama.cpp/blob/master/docs/android.md) document Android loading of selected GGUF models from app-private storage; neither runtime establishes a universal compatibility matrix. Runtime code licenses do not grant rights to a model, tokenizer, adapter, or quantization: check the exact model card/license and required notices (for example, [Gemma terms](https://ai.google.dev/gemma/terms)).

Google Play's [On-device AI delivery](https://developer.android.com/google/play/on-device-ai) offers install-time, fast-follow, and on-demand AI packs and device targeting. Fast-follow is automatic background delivery and conflicts with the product's no-auto-download rule; an on-demand request still needs transparent user choice and a supported release path. No model/optional pack is bundled or downloaded by Daymark, and no model size is currently applicable. Before any future download, first verify the target device's ABI/runtime/RAM/storage and exact model license; disclose exact artifact size, source, license, compatibility, disk use, and network/cost; require a user-started transfer; support progress, cancellation, resume, integrity verification, app-private temporary storage, cleanup, and removal. Use a trusted SHA-256/signed manifest (Android [cryptography guidance](https://developer.android.com/privacy-and-security/cryptography)); cancellation/process death does not by itself guarantee partial-file cleanup ([user-initiated transfers](https://developer.android.com/develop/background-work/background-tasks/uidt), [`DownloadManager.remove`](https://developer.android.com/reference/android/app/DownloadManager), [app-specific storage](https://developer.android.com/training/data-storage/app-specific)). Do not background-infer, auto-download, cloud-fallback, or treat downloaded executable code as model data without a separate policy review.

### Plugins, Termux/PRoot, downloads, and updates

Android [dynamic-code guidance](https://developer.android.com/privacy-and-security/risks/dynamic-code-loading) notes loaded code runs with host-app permissions; Android 14 requires dynamically loaded files be read-only ([behavior change](https://developer.android.com/about/versions/14/behavior-changes-14)). Google Play [policy](https://support.google.com/googleplay/android-developer/answer/18258653?hl=en) restricts self-updates and external downloads of executable DEX/JAR/.so; its interpreter exception is not a blanket authorization for untrusted plugins. Android's [AI excessive-agency guidance](https://developer.android.com/privacy-and-security/risks/ai-risks/excessive-agency) recommends narrow tools and avoiding open-ended shell APIs such as `Runtime.exec`. If extension support is ever justified, use typed, allowlisted, least-privilege APIs with explicit opt-in—not unrestricted shell or remotely downloaded executable plugins.

[Termux](https://github.com/termux/termux-app) is a separate no-root terminal/Linux environment; [Termux:API](https://github.com/termux/termux-api) is a signed add-on/IPC route, not generic shell access. [PRoot](https://proot-me.github.io/) uses user-space `ptrace` path translation and [PRoot-Distro](https://github.com/termux/proot-distro/blob/master/README.md) explicitly lacks kernel namespaces, cgroups, and seccomp; PRoot is not a hostile-code security boundary. Any future bridge must be user-invoked, narrowly typed, permissioned IPC, and constrained to foreground work. Daymark currently has no Termux, PRoot, plugin, or shell bridge.

Android [user-initiated data transfer jobs](https://developer.android.com/develop/background-work/background-tasks/uidt) offer visible, user-started large-transfer progress but can be stopped by system conditions; cancellation must also clean up partial artifacts. Use app-private internal storage for app-only files and the [Storage Access Framework](https://developer.android.com/training/data-storage/shared/documents-files) for explicit user-selected export. For supportable distribution, use Google Play's [managed app update](https://developer.android.com/google/play/app-updates) and optional user-visible [in-app update](https://developer.android.com/guide/playcore/in-app-updates) path for Play builds. Play policy prohibits Play-distributed self-updaters; [PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller) may require user approval and is not silent-install authority for an ordinary assistant. The current GitHub sideload path is separate and user-directed to save/open a verified APK; it is not the Play update mechanism. Check Android's [developer-verification rollout](https://developer.android.com/developer-verification/guides) before future sideload distribution. Neither app installation nor runtime/update behavior was device-tested in this review.
