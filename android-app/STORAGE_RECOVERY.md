# Encrypted task storage: failure behavior and recovery boundary

## V1 behavior

The task file is an AES-GCM encrypted snapshot in app-private storage; its non-exportable AES key is held by Android Keystore. The app distinguishes a store with no committed or in-progress file from an unreadable store:

- **No store artifacts:** this is a valid empty task list. A new Keystore key is created only when the first snapshot is saved.
- **Existing or platform-recoverable snapshot:** loading requires the existing Keystore key. The app does not generate a replacement key for an existing ciphertext.
- **Missing/unusable key, truncated or unsupported file, authentication failure, malformed task schema or scalar type, or read failure:** show “Saved tasks unavailable,” identify the broad failure class, display no ordinary empty-list invitation, and pause edits. The load path does not save or clear the task file or reset the last-known-good in-memory snapshot.
- **Interrupted update:** writes use Android `AtomicFile`; a failed stream write or explicit file-descriptor sync error calls `failWrite`, and a completed write calls `finishWrite` followed by a bounded exact-byte read-back check. The explicit sync surfaces errors returned by that sync, and read-back confirms the visible committed bytes. Some Android `AtomicFile` implementations may log a later internal sync or rename failure without throwing, so these checks do not prove durability across sudden power loss; on-device interruption testing remains required. A stale staged file without any committed/recoverable snapshot is held as an error instead of being treated as empty or overwritten. Since `AtomicFile` provides no locking, all in-process store loads/saves share a process-wide lock, and each writer rejects a snapshot whose ciphertext changed since that instance loaded it.
- **Failed edit/save:** the attempted values remain visible in the current screen and are labeled unsaved; further edits are paused. The previous committed encrypted snapshot remains the durable state. Leaving the app can discard the visible unsaved attempt; reopening may load the last committed snapshot.

The app does not delete or rotate an unavailable key, rewrite corrupt ciphertext as an empty list, or automatically replace the data with a new empty snapshot after a failure. Android `AtomicFile`'s interrupted-write rollback is the only automatic recovery behavior in scope; it is not a general corruption-repair mechanism.

## Recovery policy intentionally not selected

V1 has no task export, user-held recovery key, cloud sync, retained encrypted backup, or key-rotation recovery. Android Keystore key material is non-exportable, so replacing a missing/unusable key cannot decrypt ciphertext encrypted under the original key. Do not claim that key rotation restores tasks.

Before adding any other recovery behavior, the product owner must select and document a policy, including whether to provide a user-controlled export protected by a user-chosen recovery secret, retain a separate encrypted backup (and its retention/deletion rules), or keep failures non-recoverable. This change deliberately keeps the app at a non-destructive error state instead of selecting a backup-retention or data-loss policy.

## Attachment payloads (separate stacked feature)

Task attachment references are part of the encrypted task snapshot (new writes use schema v2; existing v1 snapshots remain readable). The actual payloads are copied only after an explicit Android `ACTION_OPEN_DOCUMENT` selection, encrypted as a stream with AES-GCM, staged under an app-owned random UUID, synced, and renamed into `noBackupFilesDir/attachments`. A separate non-exportable Android Keystore key protects payloads. The provider URI is used transiently for that copy and is not persisted, and the app requests no broad storage permission or persistable URI grant. The `*/*` picker intentionally keeps provider MIME support arbitrary; external opening is a separate conservative allowlist.

The import is capped at 20 MiB per file, 100 MiB total, 100 attachments overall, and five per task. Per-file and remaining aggregate caps are checked against actual streamed bytes, regardless of provider size hints. Import can be cancelled before task-reference commit and checks free space before and during copying. A provider read/revocation, size, cancellation, or low-space failure deletes the incomplete encrypted staging copy. If the process stops after a payload is committed but before its task reference is committed, the next successful task load removes that orphan. Removing an attachment saves the reference change before deleting the file; task deletion waits for its durable save and the existing seven-second Undo period. Startup cleanup removes unreferenced payloads and interrupted staging files. A missing referenced payload is shown as unavailable rather than treated as a missing task.

The payload file descriptor is synced before the same-directory rename, but the containing directory is not explicitly synced; durability of that directory entry across sudden power loss is not established. Process-death cleanup and encrypted stream protocol tests are JDK/source tests, not Android provider/Keystore/power-loss qualification. No device or emulator was connected for this change. A missing payload remains an unavailable attachment; a missing Keystore key has no recovery path.

Automatic backup is disabled and payloads use `noBackupFilesDir`; neither attachment ciphertext nor its Keystore key is included in Daymark backup/transfer. Clearing app data or uninstalling removes app-private files and keys. There is no in-app preview, automatic open, execution, export, cloud sync, or recovery-key flow. For an explicit user action only, files matching a conservative MIME/extension allowlist can be sent through a temporary read-only URI grant and authenticated decrypted pipe to an app the user chooses; this allowlist does not make untrusted content safe. A non-exported provider verifies the ID is still referenced by the encrypted task snapshot and re-checks the allowlist. Unknown, active-content, macro-enabled, installer and executable types stay attached but are not shared. The receiving app may retain the decrypted content, and some handlers may not support a non-seekable stream; this warning and device testing are required. Loss of the attachment key makes retained payloads unrecoverable. Personal-cloud use remains only a possible future provider-neutral, explicitly user-driven encrypted export/import direction; do not implement it until recovery, key handling, restore semantics and privacy are reviewed.

Run `sh tools/run-attachment-tests.sh` for JDK payload protocol checks and `sh tools/check-v1-source.sh` for combined core, attachment, backup, source-policy and contrast checks. These do not execute Android's picker, Android Keystore, or platform files on a device.

## Automated evidence and remaining gates

Run the JDK suite from `android-app/` with `sh tools/run-storage-recovery-tests.sh`. It exercises valid-empty versus failure, truncated ciphertext, modified AES-GCM ciphertext, missing and simulated permanently invalidated keys, an AES key rejected at initialization, partial writes, injected finish/sync failures, silently uncommitted writes, stale-snapshot rejection across two store instances, a staged first write, and failed edits that leave the previous or newer committed bytes and plaintext snapshot unchanged. Source checks verify that Activity load failures do not clear task state, loading/failure are not reported as zero tasks, failed saves are visibly unsaved and block further edits, and storage errors do not render as a normal empty list.

These tests run the production encrypted-blob protocol with a deterministic in-memory atomic-file/key adapter. They do **not** execute Android Keystore or Android `AtomicFile` on a device. Device/emulator tests for Keystore loss/invalidation, process death during writes, filesystem/storage-full behavior, startup/relaunch behavior, and TalkBack announcement/reflow remain release gates. No device installation, APK upload, or release is part of this change.

## Official Android references

- [Android `AtomicFile` API](https://developer.android.com/reference/android/util/AtomicFile): documents the complete-write/sync/commit guarantee, `startWrite`/`finishWrite`/`failWrite`, read behavior, and the caller's responsibility for mutual exclusion. Each Activity uses an I/O executor, while a process-wide lock serializes file access across Activity instances.
- [AOSP `AtomicFile` implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/util/AtomicFile.java): documents how reads handle legacy backup and staged-file cases; the app's adapter recognizes the base, `.bak`, and `.new` artifacts so absence is not confused with an interrupted write.
- [Android Keystore system](https://developer.android.com/privacy-and-security/keystore): key material remains non-exportable; the app therefore cannot recreate an unavailable original key from the ciphertext.
- [`KeyPermanentlyInvalidatedException`](https://developer.android.com/reference/android/security/keystore/KeyPermanentlyInvalidatedException): documents permanent invalidation for keys configured to require user authentication. V1's AES key does not require user authentication, but the app still treats any existing-key lookup or cryptographic key-use failure as unavailable rather than generating a substitute.
