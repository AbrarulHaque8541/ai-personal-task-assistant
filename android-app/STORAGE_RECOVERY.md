# Encrypted task storage: failure behavior and recovery boundary

## V1 behavior

The task file is an AES-GCM encrypted snapshot in app-private storage; its non-exportable AES key is held by Android Keystore. The app distinguishes a store with no committed or in-progress file from an unreadable store:

- **No store artifacts:** this is a valid empty task list. A new Keystore key is created only when the first snapshot is saved.
- **Existing or platform-recoverable snapshot:** loading requires the existing Keystore key. The app does not generate a replacement key for an existing ciphertext.
- **Missing/unusable key, truncated or unsupported file, authentication failure, malformed task schema or scalar type, or read failure:** show “Saved tasks unavailable,” identify the broad failure class, display no ordinary empty-list invitation, and pause edits. The load path does not save or clear the task file or reset the last-known-good in-memory snapshot.
- **Interrupted update:** writes use Android `AtomicFile`; a failed stream write or explicit file-descriptor sync error calls `failWrite`, and a completed write calls `finishWrite` followed by a bounded exact-byte read-back check. The explicit sync surfaces errors returned by that sync, and read-back confirms the visible committed bytes. Some Android `AtomicFile` implementations may log a later internal sync or rename failure without throwing, so these checks do not prove durability across sudden power loss; on-device interruption testing remains required. A stale staged file without any committed/recoverable snapshot is held as an error instead of being treated as empty or overwritten. Since `AtomicFile` provides no locking, all in-process store loads/saves share a process-wide lock, and each writer rejects a snapshot whose ciphertext changed since that instance loaded it.
- **Failed edit/save:** the attempted values remain visible in the current screen and are labeled unsaved; further edits are paused. The previous committed encrypted snapshot remains the durable state. Leaving the app can discard the visible unsaved attempt; reopening may load the last committed snapshot.

The app does not delete or rotate an unavailable key, rewrite corrupt ciphertext as an empty list, or automatically replace the data with a new empty snapshot after a failure. Android `AtomicFile`'s interrupted-write rollback is the only automatic recovery behavior in scope; it is not a general corruption-repair mechanism.

## Portable archive recovery and remaining boundary

The current source includes an explicitly user-triggered, SAF-only `.dmbackup` export/import flow; it is source-only and not release-qualified. Export creates a fresh exactly 32-byte CSPRNG recovery key, shown once as a checked printable code before the document picker writes the encrypted archive. The user acknowledges saving it separately; the app does not verify that action, store the recovery key or archive, or provide cloud sync. While an import waits for its recovery key, saved Activity state may retain only the selected URI and a non-secret operation token; the key is never saved. The app-private `AtomicFile` journal records the same token and exact URI before any key prompt or provider read. A recreated Activity resumes only when its explicitly restored pair matches the journal, the same-process live-operation registry, and a still-present persisted read grant. The process-local registry disappears on process death, so even a platform-restored Bundle cannot make an orphan operation look like Activity recreation. Fresh launches, mismatches, missing grants, cancellation, and abandoned operations reconcile the snapshot-last import transaction before releasing only the journaled URI's **read** grant and clearing its journal; unrelated grants and write permissions are left alone. Existing URI-only journals are treated as abandoned and cleaned after reconciliation. A recreated Activity waits for the previous in-process restore worker before startup recovery. Attachments are copied into app-owned encrypted blobs, and saved attachment references contain no source URIs. The whole archive input/output is limited to 110 MiB of actual streamed bytes. Attachment payloads remain limited to 20 MiB per file and 100 MiB total, with 100 attachments overall and five per task; import does not trust provider-reported size hints. Under the current task, attachment, text and format bounds, the maximum valid metadata manifest is 6,132,108 bytes and the maximum valid archive is 110,997,109 bytes, 4,346,251 bytes below the cap; the 10 MiB encrypted task-snapshot limit is not tighter for that maximum-metadata fixture. A real maximum-profile archive is exercised from disk. Over-cap input/output guards are also tested at the actual-byte stream boundary; an over-cap physical file with trailing padding is rejected as malformed before the reader consumes that padding. Task text and attachment names/types/contents are encrypted; outer format/version, backup ID, record types/count, exact attachment byte sizes and opaque task associations are visible. Daymark runs no vendor login, network client, upload or sync; a user-selected remote document provider may use its own network/authentication. Passphrase support is deferred.

Android Keystore key material remains non-exportable, so replacing a missing/unusable local key cannot decrypt the original local task snapshot. A previously exported archive can be restored only with its separate recovery key. Without a valid archive and key, local data remains unavailable; do not claim that key rotation restores it. The app does not retain a backup copy. Duplicate-backup history is kept locally, outside Android backup, and is removed if app data is cleared or the app is uninstalled.

## Attachment payloads (separate stacked feature)

Task attachment references are part of the encrypted task snapshot (new writes use schema v2; existing v1 snapshots remain readable). The actual payloads are copied only after an explicit Android `ACTION_OPEN_DOCUMENT` selection, encrypted as a stream with AES-GCM, staged under an app-owned random UUID, synced, and renamed into `noBackupFilesDir/attachments`. A separate non-exportable Android Keystore key protects payloads. The provider URI is used transiently for that copy and is not persisted, and the app requests no broad storage permission or persistable URI grant. The `*/*` picker intentionally keeps provider MIME support arbitrary; external opening is a separate conservative allowlist.

The attachment import is capped at 20 MiB per file, 100 MiB total, 100 attachments overall, and five per task. Per-file and remaining aggregate caps are checked against actual streamed bytes, regardless of unknown, understated, or overstated provider size hints. Portable backup parsing has its separate 110 MiB whole-archive cap, also measured from actual input bytes. Import can be cancelled before task-reference commit and checks free space before and during copying. A provider read/revocation, size, cancellation, or low-space failure deletes the incomplete encrypted staging copy. If the process stops after a payload is committed but before its task reference is committed, the next successful task load removes that orphan. If a task-reference save reports an error after the encrypted snapshot may already have committed, Daymark retains the encrypted payload; the next successful load keeps it if referenced or removes it if orphaned. Removing an attachment saves the reference change before deleting the file; task deletion waits for its durable save and the existing seven-second Undo period. Startup cleanup removes unreferenced payloads and interrupted staging files. A missing referenced payload is shown as unavailable rather than treated as a missing task.

The payload file descriptor is synced before the same-directory rename, but the containing directory is not explicitly synced; durability of that directory entry across sudden power loss is not established. JDK/source checks do not qualify Android provider pipes, Android Keystore, or power-loss behavior. A dependency-free platform instrumentation suite now exercises the real provider pipe and task metadata lookup, the Android Keystore-backed attachment adapter, and schema-v1 import/round-trip/corruption rollback. That suite must still be run on a device or emulator; none was connected for this change. A missing payload remains an unavailable attachment; a missing Keystore key has no recovery path.

Automatic Android backup is disabled and payloads use `noBackupFilesDir`; neither attachment ciphertext nor its Keystore key is included in automatic Daymark backup/transfer. Clearing app data or uninstalling removes app-private files, keys and local duplicate-backup history. There is no in-app preview, automatic open, execution, cloud sync, or retained archive. A manually exported `.dmbackup` can be moved by the user and imported as new tasks through SAF, but the app never uploads it. For an explicit user action only, files matching a conservative MIME/extension allowlist can be sent through a temporary read-only URI grant and authenticated decrypted pipe to an app the user chooses; this allowlist does not make untrusted content safe. A non-exported provider verifies the ID is still referenced by the encrypted task snapshot and re-checks the allowlist. Unknown, active-content, macro-enabled, installer and executable types stay attached but are not shared. The receiving app may retain the decrypted content, and some handlers may not support a non-seekable stream; this warning and device testing are required. Loss of the local attachment key without a valid portable archive/recovery key leaves retained payloads unrecoverable.

From `android-app/`, run `sh tools/run-portable-backup-tests.sh` for bounded archive protocol checks and `sh tools/check-v1-source.sh` for combined core, attachment, backup, fixture, source-policy and contrast checks. Those host checks do not execute Android's provider pipe or Android Keystore. Build the dependency-free Android test APK with `ANDROID_HOME=/home/ubuntu/Android/Sdk ANDROID_SDK_ROOT=/home/ubuntu/Android/Sdk ./gradlew --offline :app:assembleDebugAndroidTest`; with a device attached, install both APKs using `adb install -r app/build/outputs/apk/debug/app-debug.apk` and `adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk`, then run `adb shell am instrument -w com.cue.daymark.test/com.cue.daymark.DaymarkPlatformInstrumentation`.

## Automated evidence and remaining gates

Run the JDK suite from `android-app/` with `sh tools/run-storage-recovery-tests.sh`. It exercises valid-empty versus failure, truncated ciphertext, modified AES-GCM ciphertext, missing and simulated permanently invalidated keys, an AES key rejected at initialization, partial writes, injected finish/sync failures, silently uncommitted writes, stale-snapshot rejection across two store instances, a staged first write, and failed edits that leave the previous or newer committed bytes and plaintext snapshot unchanged. Source checks verify that Activity load failures do not clear task state, loading/failure are not reported as zero tasks, failed saves are visibly unsaved and block further edits, and storage errors do not render as a normal empty list.

The host storage tests run the production encrypted-blob protocol with deterministic in-memory atomic-file/key adapters; they do **not** execute Android Keystore or Android `AtomicFile`. The Android instrumentation source additionally exercises a real `AtomicFile`, a real `AttachmentContentProvider` pipe and metadata transaction, schema-v1 import/migration/rollback, removal of the source Android Keystore alias before portable restore, destination-key re-encryption, full-archive validation before local staging, and simulated process death before/after the task-snapshot commit. Host state-machine checks exercise URI-and-token-bound Activity recreation with a readable selected document, fresh-launch/process-death cleanup, cancellation, URI mismatch and revoked-grant cleanup, recovery-key exclusion from saved state, active-worker coordination, and reconcile-before-release behavior. These instrumentation tests were **compiled but not run** here: the SDK `adb devices -l` list was empty, and no emulator binary or AVD is installed. Real Keystore lifecycle, storage-full/provider behavior, SAF grant persistence/release, startup/relaunch, and TalkBack announcement/reflow remain device release gates. No device installation, APK upload, or release is part of this change.

## Official Android references

- [Android `AtomicFile` API](https://developer.android.com/reference/android/util/AtomicFile): documents the complete-write/sync/commit guarantee, `startWrite`/`finishWrite`/`failWrite`, read behavior, and the caller's responsibility for mutual exclusion. Each Activity uses an I/O executor, while a process-wide lock serializes file access across Activity instances.
- [AOSP `AtomicFile` implementation](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/util/AtomicFile.java): documents how reads handle legacy backup and staged-file cases; the app's adapter recognizes the base, `.bak`, and `.new` artifacts so absence is not confused with an interrupted write.
- [Android Keystore system](https://developer.android.com/privacy-and-security/keystore): key material remains non-exportable; the app therefore cannot recreate an unavailable original key from the ciphertext.
- [`KeyPermanentlyInvalidatedException`](https://developer.android.com/reference/android/security/keystore/KeyPermanentlyInvalidatedException): documents permanent invalidation for keys configured to require user authentication. V1's AES key does not require user authentication, but the app still treats any existing-key lookup or cryptographic key-use failure as unavailable rather than generating a substitute.
